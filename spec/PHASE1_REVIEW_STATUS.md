## 2. 两个仓库的统一对齐规则

后续所有功能 Review 固定遵循以下规则：

1. `spec/PRODUCT_AND_BUSINESS_DECISIONS.md` 是最终业务基线。
2. `datax-lite-jdk21/master` 当前可达的 Controller、Service、Repository、前端路由和菜单，用于确认老系统实际具备的功能。
3. 老系统实际功能如果已经被新文档明确删除或改变，以新文档为准，不保留旧实现兼容分支。
4. 老系统实际存在、新文档没有明确删除的功能，默认保留其业务能力。
5. 保留业务能力不等于复制旧表、旧字段、旧默认值、旧状态机或旧实现类。
6. 历史 Spec、过期说明文档、孤立实体、孤立 Repository 或不可达代码，不能单独证明功能仍需进入新系统。
7. 旧代码说明文档与当前可达代码不一致时，以当前代码为老功能事实源。
8. 只有同时存在真实代码/调用路径证据，以及与新业务基线的明确冲突或目标模型缺口时，才记录为问题；不得根据可能性虚构需求。
9. 能从业务基线和代码直接判断的技术细节直接完成，只在存在真实业务选择时逐项确认。
10. 每次只讨论一个真实问题；确认后更新相应文档和 `spec/TASKS.md`，并提交到 `main`。

## 4. 已确认的核心业务和目标模型

### 4.1 新旧系统和数据库隔离

已经确认：

- 老系统继续连接原 `df_ygt/df_etl` PostgreSQL 数据库运行，直到新系统完成验收和正式替换；
- 新系统使用完全独立的新 PostgreSQL 数据库；
- 新系统不得修改、认领、升级或 Flyway baseline 老数据库；
- 老库 Schema 快照只作为历史结构证据；
- 新系统最终从干净的 Flyway V1 开始；
- 老 Quartz 运行态、旧执行历史和废止模型默认不迁移；
- 最终需要迁移哪些配置，在替换阶段通过 `DB-002` 单独确定。

### 4.2 医共体和机构

已经确认：

- 一个部署和一套独立元数据库只服务一个医共体；
- 医共体名称和编码保存为系统设置；
- 不建立租户表，不在业务表重复保存 `community_id`；
- 机构采用扁平集合，不建立父子层级；
- 机构编码在当前系统范围内全局唯一；
- 源视图中的医疗机构代码必须与机构管理中的机构编码一致；
- 不维护厂商内部机构代码映射。

### 4.3 业务系统实例和数据源

已经确认：

- 业务系统实例与机构为多对多；
- 业务系统实例与源数据源为多对多；
- 一个实例可以关联多个源数据源；
- 一个源数据源可以承载多个逻辑系统实例；
- 实例与源数据源的关系是纯关联关系，不保存用途、优先级或自动切换策略；
- 源数据源支持 `HOST_PORT` 和完整 JDBC URL 两种连接方式；
- 用户名、密码等凭据单独保存，不嵌入 JDBC URL；
- Doris 按一个逻辑部署管理，支持单机或多个 FE，不管理 BE；
- 数据源组和任务组不进入新系统。

### 4.4 标准数据集和版本

已经确认：

- 标准数据集只能由管理员从医共体数据模型人工同步；
- 不允许在数据集管理中手工新增；
- 不设置自动同步；
- 只有规范化定义内容和 `definition_hash` 变化时才生成不可变新版本；
- 内容未变化时只更新同步时间和同步结果；
- 数据集身份、不可变版本、字段版本和转换合同分离；
- 新数据集版本不会自动修改旧链路、旧任务或 Doris；
- 管理员按人工流程核对链路、源视图和字段解析结果，再显式生成新链路版本、任务版本或重建任务。

### 4.5 字段解析和转换合同

已经确认：

- 医疗字段转换合同同时服务于 Doris DDL、Reader、数据预检和 Checksum；
- 医疗标准字段转换与通用 JDBC→Doris 类型建议是两套不同合同；
- 标准字段和源字段只允许大小写差异；
- 不支持别名、人工重命名、默认值或转换表达式改变字段身份；
- 每个标准字段必须在 JDBC 元数据中大小写不敏感地唯一命中；
- 源字段集合与标准字段集合必须完全相等；
- 源字段按大小写折叠后重名时必须报错；
- Reader 按标准合同顺序显式投影，不要求源字段物理顺序一致；
- Reader、机构过滤、增量窗口、预检和 Checksum 共用同一份只读字段解析快照；
- Doris 业务字段固定使用标准字段的小写名称。

### 4.6 Doris ODS/RAW 固定存储合同

已经确认：

- 每个标准数据集在一个逻辑 Doris 部署中固定使用一张 ODS 和一张 RAW；
- 多家机构共享同一张物理表，通过标准医疗机构编码隔离；
- PostgreSQL 不建立 Doris 物理表登记表或结构版本表；
- 平台直接读取 Doris 实际元数据并与目标合同比较；
- 普通同步只校验结构，不自动建表、补列或修改结构；
- 建表和重建只能由用户显式发起；
- ODS 严格遵循医疗字段合同；
- RAW 固定用于预检，业务字段全部使用可空字符串保存原始值；
- ODS 和 RAW 不能相互转换；
- 不提供可配置的“严格/宽松”正式表模式；
- 删除扫描全部任务并自动执行 Doris 列类型修正/ALTER 的旧能力。

### 4.7 采集链路

已经确认：

- 同一业务系统实例、源数据源、标准数据集和源对象只建立一条链路；
- 一条链路可以覆盖多个机构；
- 不因共享视图包含多家机构而复制相同链路；
- 链路身份和不可变链路版本分离；
- 只有规范化配置内容变化时才生成新链路版本；
- 重复核对且内容未变化时不生成版本；
- 链路不保存运行状态、最近同步或任务状态；
- 链路不保存结构检查门禁状态；
- 结构检查并入预检第一阶段；
- 结构或预检问题只展示风险，不阻止任务创建和运行；
- 链路使用逻辑删除；
- 已有未删除任务引用时不得删除链路。

### 4.8 同步任务、任务版本和唯一性

已经确认：

- 一个同步任务只属于一家医疗机构和一个标准数据集；
- 同一机构、同一数据集只能存在一个未删除任务；
- 同一共享链路可以为不同机构分别创建单机构任务；
- 单机构任务使用标准医疗机构代码过滤源数据；
- 唯一性必须由 PostgreSQL 部分唯一索引最终保证；
- 任务身份和不可变任务版本分离；
- 当前版本由 `current_version_id` 指针确定；
- 不保存与执行结果重复的任务生命周期状态；
- 暂停任务只设置 `schedule_enabled=false`；
- 暂停后仍允许人工运行；
- 删除任务为逻辑删除；
- 运行中的任务禁止删除；
- 历史任务版本、执行、批次、水位、校验、消息和审计全部保留。

### 4.9 三种标准任务类型

已经确认：

| 数据集条件 | 固定任务组合 |
| --- | --- |
| 无业务主键 | `FULL_ONLY + TRUNCATE + DUPLICATE_KEY` |
| 有业务主键且有有效增量字段 | `FULL_THEN_INCREMENT + UPSERT + UNIQUE_KEY` |
| 有业务主键但没有有效增量字段 | `FULL_ONLY + UPSERT + UNIQUE_KEY` |

同时确认：

- 无主键任务不生成 Hash、自增 ID、`row_number()` 等假主键；
- 多机构共享 ODS 时，无主键任务只清理当前机构范围，禁止清空整张物理表；
- `_etl_job_id` 只用于内部追踪，不能作为业务主键或唯一清理条件；
- 三种标准任务不使用 APPEND 作为默认写入方式。

### 4.10 调度、失败、取消和人工恢复

已经确认：

- 第一阶段 Reader 固定单并发；
- Fetch Size 可以配置；
- 同一任务禁止并发执行；
- 任务运行期间到达的新计划调度直接跳过；
- 不建立待追赶状态，也不在当前执行完成后自动补跑；
- 正式同步失败只告警，不自动暂停任务；
- 下一次计划调度仍正常执行；
- 不自动重试，不做指数退避；
- 不支持从失败批次继续；
- 普通失败只提供人工“重新采集”；
- 重新采集创建新的独立执行，从任务范围起点和第 1 批重新读取；
- 数据补采是独立业务命令，不修改正式水位；
- 取消执行只终止当前执行，不修改调度开关；
- 暂停任务和取消执行是两个独立操作；
- 不建立 `execution_checkpoint`、`execution_reconciliation`、跨执行恢复字段或独立重试来源字段。

### 4.11 正式水位、载入批次和 Doris Label

已经确认：

- `task_watermark` 只保存当前正式水位和最后成功执行；
- 不建立 `task_watermark_history`；
- 正常水位推进可从成功执行的固定窗口追溯；
- 人工重置水位的前后值、原因和操作者写入 `audit_log`；
- 每个载入批次保存真实游标范围、时间窗口、机构范围、行数、Checksum、确定性 Doris Label 和最终状态；
- Doris 响应不明确时先查询原 Label；
- Label 探测结果直接写入 `load_batch`；
- `load_batch` 只表示当前执行的批次进度，不作为下一次执行的跨执行恢复检查点。

### 4.12 数据预检

已经确认：

- 预检只能由用户人工发起；
- 每次固定扫描整条采集链路；
- 不提供只运行某一家机构的模式；
- 结构检查是预检第一阶段；
- 预检不是任务创建和运行门禁；
- 同一链路同一时间只允许一个活动预检；
- 不同链路的并发上限由全局参数控制；
- RAW 按 `run_id + route_id` 隔离；
- RAW 终态后保留 1 天；
- 执行状态和结果状态分开；
- 完整扫描发现不合格数据是“完成 + 有问题”，不是技术失败；
- 只保存字段级和组合规则级汇总；
- 不保存行级问题、业务主键、原值、修正值、严重级别或处理状态；
- 按筛选条件直接导出 XLSX/CSV 汇总；
- 不建立异步导出任务表或长期导出文件。

### 4.13 数据校验

已经确认：

- 正式同步默认自动执行零容差 `ROW_COUNT`；
- 用户可以在数据集或任务级手工改为 `ROW_COUNT_CHECKSUM`；
- 平台不自动判断哪些数据属于核心数据；
- 只有真实业务主键的数据集才能使用内容 Checksum；
- 无业务主键数据集固定使用 `ROW_COUNT`；
- 不允许因为缺少比对键、性能或数据量静默降级；
- Checksum 覆盖当前数据集版本的全部业务字段；
- `_etl_*` 字段不参与 Checksum；
- 默认 `lookbackHours=0`；
- 取消默认自动复检；
- 人工重新校验创建独立运行；
- 内部可以分批计算，但只持久化整次最终结果；
- 不建立校验分段表、行级差异表、字段差异表或自动修复状态；
- 小型差异汇总保存到 `validation_run.difference_summary JSONB`；
- 最终阻断校验通过后，才能确认执行成功、推进水位并生成消息 Outbox。

### 4.14 删除识别业务规则

业务语义已经确认：

- 使用定期主键快照识别源端物理删除；
- 第一次完整快照建立有效基线；
- 后续完整快照与上一份有效基线比较；
- 失败或不完整快照不能替换有效基线；
- 第一阶段只形成删除差异；
- 不自动删除 Doris 正式数据；
- 实际应用删除必须经过 dry-run、权限校验、二次确认和审计。

该能力的持久化模型尚未完整设计，见第 8 节。

### 4.15 消息通知和事务 Outbox

消息模型已经全部 Review 完成：

- P0 只使用 RabbitMQ；
- 删除 Redis Stream；
- 消息配置只存在于数据集级；
- 三个启用消息的数据集分别维护策略；
- Exchange 固定为 `YL`；
- Routing Key、topic、`messageKey`、空值处理和 27 位 `messageId` 沿用旧消费协议；
- 全量执行发送本次全量的全部数据；
- 增量执行发送本次增量的全部数据；
- 不支持 `SKIP`、`NOTIFY_ONLY`、完成通知或 TRUNCATE 信号；
- 每次执行只创建一条小型 `message_outbox` 发布指令；
- Outbox 不保存业务数据、分页进度、逐条消息明细或投递尝试明细；
- Outbox 状态固定为 `PENDING/PUBLISHING/PUBLISHED/DEAD_LETTER`；
- 不设置 `FAILED`、`next_attempt_at`、`provider_message_id` 或 `event_type`；
- 临时失败回到 `PENDING`，耗尽次数进入 `DEAD_LETTER`；
- 人工重发从 `DEAD_LETTER` 回到 `PENDING`；
- 重发重新读取当前 Doris，不保存原执行业务数据快照；
- `PUBLISHED/DEAD_LETTER` 长期保留，P0 不自动清理或归档；
- 任务逻辑删除不级联删除历史 Outbox。

### 4.16 外部任务 API

已经确认：外部任务 API 属于阶段 1 P0，不再讨论是否保留。

核心业务输入仍然是：

```text
医疗机构编码 + 数据集标识（单个或多个）
```

旧当前 DTO 中的 `requestId`、`runAfterCreate` 和 `failurePolicy` 分别用于幂等、是否立即运行和批量失败处理，不是同步、校验或消息业务策略。

新系统不根据过期旧文档增加以下业务参数：

- 源数据源；
- 源 Schema 或源对象；
- Doris 表名；
- 同步策略；
- 校验策略；
- 消息策略；
- 字段映射或自定义 SQL。

需要保留的实际功能：

- 外部 client 管理；
- secret 生成、重置、启停；
- HMAC-SHA256；
- timestamp 和 nonce 防重放；
- 创建前规划；
- 按机构和数据集创建任务；
- 查询任务；
- 运行任务；
- 删除任务；
- 批量请求幂等；
- 查询消息发布状态；
- 人工重发消息。

外部创建任务必须调用新的任务领域服务，原子创建任务和第一个不可变任务版本，不能直接写旧的扁平任务表。

旧外部 API 当前请求 DTO 从未提供消息策略参数，因此“不允许外部 API 覆盖消息策略”不是一个实际存在的迁移问题，后续不再作为 Review 议题。

- 批量任务模板；
- 机构数据视图；

## 7. 尚需业务确认的事项

在没有确认前，不自行扩大授权模型。

### 7.3 外部 API 是否新增限流

旧代码没有找到 client 级限流器、HTTP 429 路径或限流状态表，因此限流不是老功能迁移内容。
