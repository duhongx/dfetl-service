# 当前已确认的执行流程规则

> 状态：当前有效  
> 整理日期：2026-08-17  
> 可信基线：`341e3b5d070e5b2a242457c74d325ca7639c43d4`  
> 适用范围：数据预检、正式同步、无主键机构范围替换、同步后校验、RabbitMQ 数据集级消息、阶段状态  
> 边界：本文只记录用户已经明确确认的流程规则，不定义新的资源模型、物理表、API、前端页面或 Flyway 结构。

## 1. 优先级

发生冲突时按以下顺序处理：

1. 用户最新明确确认；
2. 本文件；
3. `PRODUCT_AND_BUSINESS_DECISIONS.md`；
4. `TARGET_METADATA_MODEL.md` 和 `TASKS.md`；
5. 历史审计、旧代码和归档材料。

本文没有将任何后续规划稿中的“业务目录、单机构采集路由、无任务版本当前配置”等模型重新确认为现行模型。

## 2. 数据预检

### 2.1 启动和并发

- 数据预检只允许人工启动，不设置自动调度。
- 同一采集链路同时最多运行一个预检。
- 不同采集链路可以并行，最大并行数由全局参数控制。
- 重新预检始终创建新的运行记录，并从本次预检范围起点重新开始，不续接上一次运行。

### 2.2 目的、问题明细和汇总

- 预检用于发现源表或源视图的结构与数据质量问题，供源数据提供方修正。
- 预检结果必须能够定位到具体问题记录，并说明该记录的哪些字段不合法以及对应原因，例如非空字段为空、长度超出、类型或格式错误、日期时间错误、数值精度或小数位错误、值域错误、业务主键问题和组合规则问题。
- 问题记录明细是整改依据，不等同于随机抽取或脱离问题上下文的“数据样例”；普通样例页可以不提供，但不能因此取消问题明细。
- 字段级、规则级和机构级汇总必须保留，用于统计、筛选和趋势分析；汇总不能替代问题记录明细。
- 数据集存在真实业务主键时，问题记录使用“机构代码 + 标准业务主键”定位；数据集没有真实业务主键时，允许使用只在本次预检运行内有效的技术定位符定位问题记录。
- 运行内技术定位符只能用于本次预检查询、整改和导出，不得作为正式同步业务主键、增量游标、Doris `UNIQUE KEY`、删除对账键或 `ROW_COUNT_CHECKSUM` 对齐键。

### 2.3 保存、权限和导出边界

- 预检运行记录及字段级、规则级、机构级汇总作为审计和质量趋势依据长期保留。
- 问题记录明细及用于还原问题上下文的原始预检数据按限期保留策略管理，不要求永久保存完整源数据。
- 明细页面默认按敏感字段规则掩码；查看原值和导出问题明细使用独立权限并记录操作审计。
- 问题明细的最终存储介质、默认保留期、最大保留期、同步或异步导出方式及大数据量限制，仍属于后续产品和物理模型 Review；确认前不得擅自固定为 PostgreSQL 明细表、固定 Doris 表或固定天数。
- 明细到期清理后仍可查看长期汇总，但页面必须明确提示明细已清理以及清理时间。

### 2.4 与正式同步的边界

- 预检不写入正式 ODS，不作为正式同步的数据来源。
- 预检不得自动修复、静默过滤、只同步合规行或把预检中间结果直接提升为正式业务数据。
- 源数据提供方修正源表或源视图后，用户可以重新发起预检。
- 正式同步始终重新读取真实源表或源视图；预检通过不代表复用 `raw_`、问题明细或其他预检暂存数据。

本节明确覆盖可信交接文档中“只保存汇总、不提供问题记录明细”的旧描述；核心产品、目标模型和任务清单必须与本节保持一致。

## 3. 正式同步

- 正式同步与数据预检是两条独立流程。
- 正式同步按任务合同执行全量或周期增量读取，数据来源始终是真实源表或源视图。
- 失败后的普通恢复使用新的重新采集执行，从本次数据范围起点和第 1 批重新读取，不把历史成功批次当作跨执行断点。
- 数据补采是独立执行，只处理用户明确指定的历史时间范围或业务主键范围，不修改正常任务的正式水位。
- Doris Stream Load 返回不明确时，先查询原 Label 的最终状态；不得生成新 Label 盲目重投同一批数据。
- 只有本次写入完成且阻断型同步后校验通过，执行才能确认成功并推进正式水位。
- 写入失败、校验不一致、校验执行失败或取消时，不推进正式水位。

### 3.1 无业务主键任务的机构范围替换

- 无业务主键标准任务的统一业务合同为 `FULL_ONLY + REPLACE_INSTITUTION_SCOPE + DUPLICATE_KEY`。
- `REPLACE_INSTITUTION_SCOPE` 表示“以源端当前机构完整快照替换 Doris 中该机构范围”，不是数据库物理命令名称。
- 旧文档中的 `FULL_ONLY + TRUNCATE + DUPLICATE_KEY` 仅作为历史术语；当前实现不得把它映射为整表 `TRUNCATE TABLE`、SeaTunnel `DROP_DATA` 或其他会清空共享表全部机构数据的操作。
- 底层优先采用能够先完整装载和校验、再原子替换当前机构分区或范围的方案；无法原子替换时，必须单独 Review staging、失败恢复、查询空窗和机构隔离，不得简单“先删当前机构、再边读边逐批写入”。
- 无论采用何种物理策略，都必须证明只影响当前任务所属机构，其他机构数据保持不变。
- 具体 Doris 分区、临时分区、staging 或条件删除实现仍属于物理设计 Review；本规则只冻结业务语义，不授权立即修改 Doris DDL 或执行代码。

## 4. 同步后校验

- 数据预检用于同步前发现源端问题；数据校验用于同步后核对本次实际源端载荷和 Doris 结果，两者不得混用。
- 正式同步默认执行零容差 `ROW_COUNT`。
- 只有数据集合同具有真实业务主键时，才允许选择 `ROW_COUNT_CHECKSUM`；机构代码、技术分片字段、Hash、自增 ID 或 `row_number()` 等不能冒充业务主键。
- 选定的校验方法必须严格执行，不能静默从 `ROW_COUNT_CHECKSUM` 降级为 `ROW_COUNT`。
- 校验范围必须与本次执行实际读取和写入的机构及数据范围一致。
- 人工重新校验必须基于原执行已经固定的身份、合同和范围，不能用后来修改的当前配置替换历史上下文。
- 阻断型校验通过后，才能确认执行成功、提交正式水位并生成本次消息 Outbox；校验失败或不一致时保留上一次成功水位。
- 默认不进行延迟自动复检；人工重新校验创建独立运行记录。

## 5. RabbitMQ 数据集级消息

- P0 只使用 RabbitMQ，不使用 Redis Stream，也不提供运行时传输通道切换。
- 消息配置只存在于数据集级，不提供任务级覆盖。
- 允许启用业务消息的数据集限定为：
  - `YL_HUANZHEJBXX`
  - `YL_KESHIXX`
  - `YL_ZHIGONGXX`
- 全量同步和增量同步都发布本次成功执行有效范围内的全部业务数据，即固定 `ALL` 语义。
- `ALL` 是固定发布行为，不是可编辑的 `full_sync_mode`；不支持 `SKIP`、`NOTIFY_ONLY`、全量完成通知或 TRUNCATE 信号。
- 空值处理继续遵循与消息消费方已经协商的既有合同；本次 Spec 清理不得擅自改变空值含义、丢弃空值字段或替消费方重写数据。
- 每次执行在接受任务时固定本次生效的数据集消息策略；后续策略修改不改变已经启动的执行。
- 只有正式同步和阻断型校验成功后，才创建本次唯一的 Outbox 发布指令。
- 执行成功、正式水位提交和 Outbox 创建在同一 PostgreSQL 事务内完成；事务内不直接访问 RabbitMQ。
- RabbitMQ 投递失败不回滚已经成功的同步和水位，通过 Outbox 重试或人工重发恢复。
- RabbitMQ 连接参数属于部署配置；固定持久化 Topic Exchange `YL`，使用持久化消息及 Publisher Confirm/Return。
