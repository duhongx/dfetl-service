## 1. 项目目标

本阶段把已经迁移的 Java 服务和现有 Web 前端整合为可运行的 DFETL 系统，优先保证以下业务闭环：

1. 医共体数据定义同步为标准数据集。
2. 通过业务系统实例灵活组织数据源与覆盖机构，并为机构配置采集链路。
3. 基于有效采集链路和最终生效的预检策略创建同步任务。
4. 执行全量及增量数据同步，正确维护水位。
5. 按配置执行数据校验，校验未通过时按策略阻断水位推进。
6. 支持任务监控、问题诊断、告警、日志和审计。
7. 前端所有可见按钮均有明确、可验证的业务行为。

## 2. 业务边界

### 2.1 数据集

- 数据集以医共体数据模型为唯一来源。
- 数据集管理不提供手工新增、手工删除功能。
- 同步医共体定义时记录首次入库时间、最近同步时间、定义版本和合同 Hash。
- 数据集详情必须包含：
  - 基础信息
  - 字段结构
  - 同步策略
  - 数据校验
  - 消息通知
- 可继承的业务策略采用“全局默认 → 数据集覆盖 → 任务覆盖”三级模型；任务运行记录保存实际生效值及来源。
- 是否自动把上游策略更新应用到已有任务，见待确认事项 D-006。

### 2.2 业务系统实例

- “业务系统实例”表示医共体内实际部署的一套业务系统，不以厂商作为唯一标识。
- 同一厂商可以在一个医共体内部署多套独立系统实例。
- 一个业务系统实例可以覆盖全部机构，也可以只覆盖任意一组机构。
- 一个机构可以同时接入多套业务系统实例，例如 HIS、LIS、PACS，或处于迁移期的新旧两套 HIS。
- 业务系统实例与机构为多对多关系。
- 业务系统实例与源数据源为多对多关系：一套系统可跨多个数据库，一个数据库也可承载多个逻辑系统实例。
- 采集链路必须明确标准数据集、业务系统实例、源数据源、Schema 和源对象，并记录其覆盖的机构范围。
- 当一套共享业务系统的源对象包含多家机构数据时，以标准字段中的医疗机构代码区分机构；医疗机构代码必须参与联合业务主键。
- 源视图中的医疗机构代码必须与“机构管理”保存的机构编码完全一致，且机构编码全局唯一。
- 不建立厂商内部机构代码与标准机构编码之间的二次映射，也不在业务系统实例覆盖关系中增加“源系统机构代码”字段。
- 同一源对象不因覆盖多家机构而机械拆分成多条重复链路。
- 厂商、系统类型和版本用于描述、筛选和统计，不能作为自动合并系统实例的依据。

### 2.3 数据预检

- 数据预检与正式数据同步相互独立，是可配置能力，不是系统硬编码的必经步骤。
- 预检只用于发现源视图的数据质量和结构问题，不写入正式业务表。
- 预检需定位到具体业务主键、字段、原始值、标准规则和错误原因。
- 预检通过后，正式同步仍从源视图重新提取数据。
- 预检结果绑定采集链路版本、数据集合同 Hash 和源对象结构 Hash。
- 预检策略支持三级继承：全局默认 → 数据集覆盖 → 任务覆盖；数据集和任务均可选择“继承上级”。
- 最终生效模式包括：
  - **关闭（DISABLED）**：不要求预检结果，允许直接创建和运行任务。
  - **提示（ADVISORY）**：缺少预检、预检有问题或结果过期时展示风险，但不阻断创建和运行。
  - **强制（REQUIRED）**：创建和运行前必须存在与当前链路版本及 Hash 匹配的有效通过结果。
- 不预检或选择提示模式会提高正式同步失败概率；系统明确展示风险并记录审计，但不代替使用者作业务决策。
- 预检执行时必须检查医疗机构代码非空、存在、启用且属于当前链路覆盖范围；空值、未知、停用或越界均记录为可定位的阻断级问题。
- “阻断级问题”表示问题严重度；其是否阻止任务创建或启动，仍由最终生效的预检模式决定。
- 即使关闭预检，正式 ODS 写入的最低技术契约和目标表约束仍然生效，遇到不合规数据时任务可以在运行阶段明确失败。

### 2.4 数据同步

- 同步任务必须来源于一条有效采集链路，不允许绕过链路直接拼装源、目标配置。
- 初次执行支持全量；后续按策略执行增量。
- 任务运行前必须重新检查链路、数据源、目标源和任务快照，并按最终生效的预检策略处理预检结果。
- 数据集定义变更不做在线热更新，统一按人工维护流程处理。
- 水位只能在写入成功且阻断型校验通过后推进。
- DFETL 明确定义三种不同的数据读取操作，前端入口、服务端命令、权限、确认提示和审计记录不得混用：
  1. **重试**：用于普通任务失败，默认从最后成功检查点继续。已成功提交到 Doris 的载入批次予以保留，从失败批次恢复并继续处理剩余批次；重试成功且整次执行校验通过后才推进任务水位。
  2. **重新采集**：从任务数据范围起点重新读取全部数据。默认使用 UPSERT 幂等覆盖目标表中已有记录，不主动清理目标数据；只有用户明确选择“清空重建”时才清理目标范围，并且必须二次确认、执行引用检查和记录审计。
  3. **数据补采**：针对一个已经结束的历史时间窗口或主键范围重新读取，例如补采 `2026-08-01 00:00～12:00`。数据补采是独立执行，不作为普通运行失败的恢复方式，不修改正常任务的失败检查点。
- 每个载入批次必须记录检查点及 Doris Stream Load Label/事务状态。遇到响应不明确时先查询 Label 状态，禁止仅凭客户端异常重复写入或跳过批次。
- 第一阶段采用单 Reader、单个在途写入批次；只有当前批次确认提交成功后才读取并提交下一个批次，保证“最后成功检查点”含义确定。
- 示例：全量任务共 240 个载入批次，第 120 批失败时，第 1～119 批保留，第 120～240 批由“重试”恢复；“重新采集”才会从第 1 批重新读取，“数据补采”仅用于另行指定的历史范围。

### 2.5 数据校验

- 数据预检用于正式同步前的数据质量检查。
- 数据校验用于同步后核对源端与目标端一致性。
- 校验方式必须严格执行任务配置，不能用行数校验替代 Checksum。
- Checksum 范围为当前版本医共体数据集定义中的全部字段；DFETL 内部新增的 `_etl_*` 维护字段不参与 Checksum。
- 为避免跨数据库表示差异造成误报，参与 Checksum 的字段必须按统一规则规范化空值、日期时间、数值精度、字符和字段顺序。
- 与同步批次绑定的阻断校验失败时，该执行批次直接判定为失败；任务水位保留在上一次成功提交的位置。
- 全量校验、修改校验和删除校验分别保留独立的执行语义和历史记录。

### 2.6 Doris 建表模式与质量责任

DFETL 支持两种目标表建模策略，模式在 Doris 建表、链路、任务快照、执行和校验中保持一致：

1. **严格模式（STRICT）**
   - 以当前版本医共体数据集定义为唯一目标结构。
   - 按标准字段生成精确 Doris 类型、长度、精度、联合主键及 NOT NULL 约束。
   - 违反标准格式、长度、精度、非空、主键或机构范围的记录不能作为成功批次静默跳过。
   - 若最终预检策略为强制，正式运行前必须通过有效预检；若配置为提示或关闭，则允许直接运行，但目标约束导致的数据错误会使任务在运行阶段失败。
   - 任一载入批次因数据质量问题失败时，任务失败并保留原水位，业务系统整改源视图后执行“重试”。

2. **宽松模式（PERMISSIVE）**
   - 目标表结构根据源对象的 JDBC 元数据生成，不以医共体字段格式作为一般业务字段的写入约束。
   - 目标表采用 UNIQUE KEY Merge-on-Write，以“医疗机构代码 + 数据集联合业务主键”作为记录唯一标识。
   - 联合业务主键字段必须非空并可唯一标识记录；这是正式 ODS 写入的最低技术契约。
   - 除联合业务主键外，其他业务字段允许 NULL；不应用医共体定义中的长度、格式、值域及非主键 NOT NULL 质量约束。
   - 类型映射优先保证源数据可落库；无法安全映射的源类型使用可完整承载其文本表示的宽松类型。
   - 预检仍可按关闭、提示或强制配置；建表模式本身不替使用者决定是否必须预检。
   - 除最低主键契约外，医共体定义符合性及源数据质量由业务系统负责。
   - 源查询、网络、认证、序列化或 Doris 技术故障仍会导致任务失败。

共同边界：

- 建表模式与预检策略相互独立：前者决定目标结构和运行时约束，后者决定正式运行前的检查与门禁行为。
- 系统提供灵活配置并如实执行，不用硬编码替代使用者决策；同时明确展示最终生效值、风险、来源和运行结果。
- 建表模式必须持久化到目标表元数据、采集链路和任务快照。
- 预检策略的任务快照和每次运行记录必须保存最终生效模式，以及该值来自全局、数据集还是任务覆盖。
- 行数和 Checksum 属于传输一致性校验；严格和宽松模式均可启用。
- 宽松模式不允许静默丢行。
- 已存在目标表切换建表模式时不自动原地修改表结构；必须结构评估、重建确认和审计。
- 同一目标表上的任务继承该表实际建表模式，不允许运行时临时切换。

## M1：核心领域模型整改

### [P0][SRC-001] 建立灵活的业务系统实例模型

现状：`SourceDataSource` 只有一个 `institutionId`，既不能表达一套区域 HIS 覆盖全部医疗机构，也不能表达医共体内多套 HIS 分别覆盖不同机构组的情况。

已确认模型：

- `business_system_instance`：表示实际部署的一套业务系统。
- `business_system_instance_institution`：维护系统实例与覆盖机构的多对多关系。
- `business_system_instance_datasource`：维护系统实例与源数据源的多对多关系。
- 采集链路归属于业务系统实例和数据源，并记录覆盖机构集合；不再强制每家机构各建一条重复链路。
- 对共享源对象，任务按一条链路采集覆盖范围内的多家机构数据，依靠医疗机构代码联合主键保证机构隔离和数据唯一性。

任务：

- [ ] 新增业务系统实例实体、接口、数据库迁移及启停状态。
- [ ] 实例属性至少包含：编码、名称、系统类型、厂商、版本、状态和说明。
- [ ] 支持一个实例覆盖全部机构或任意机构子集。
- [ ] 支持一个机构关联多套系统实例。
- [ ] 支持一个实例关联一个或多个源数据源。
- [ ] 支持同一源数据源承载一个或多个逻辑系统实例。
- [ ] 数据源与机构的可选范围通过系统实例关系计算，不再使用单一 `institutionId` 硬编码限制。
- [ ] 新建链路时依次选择系统实例、标准数据集、数据源、Schema 和源对象，并从系统实例覆盖范围内确认链路覆盖机构。
- [ ] 校验链路覆盖机构必须属于系统实例覆盖范围，所选数据源必须与实例有关联。
- [ ] 校验标准数据集中医疗机构代码字段存在、启用且属于联合主键。
- [ ] 源视图医疗机构代码直接使用机构主数据编码，不提供厂商内部代码映射实体、字段或配置入口。
- [ ] 同一系统实例、数据源、标准数据集和源对象组合只建立一条有效链路，避免按机构重复采集同一共享视图。
- [ ] 厂商仅作为实例属性；相同厂商的多套部署不得自动合并。
- [ ] 删除或停用实例前检查机构关联、数据源、链路和任务引用。
- [ ] 机构、数据源和链路列表展示对应系统实例及覆盖范围。

验收场景：

1. **全区域一套 HIS**：一个区域 HIS 实例关联县人民医院、县中医院、县妇保院和 9 家乡镇卫生院，可只关联一个共享数据源。
2. **多套 HIS 分组覆盖**：人民医院实例覆盖人民医院及部分乡镇；中医院实例覆盖中医院及部分乡镇；妇保院实例只覆盖妇保院，各实例使用自己的数据源。
3. **同机构多系统**：同一家机构可同时关联 HIS、LIS、PACS 等实例，采集链路按数据集选择正确实例和数据源。
4. **同厂商多实例**：同一厂商在不同机构组部署的两套 HIS 保持为两个独立实例。
5. **共享视图多机构采集**：同一源对象包含多家机构数据时，只建立一条覆盖对应机构集合的采集链路；医疗机构代码参与联合主键，任务、预检、校验和统计既可按链路汇总，也可按机构代码下钻。
6. **独立数据源/独立视图**：不同系统实例或不同源对象仍分别建立链路，不因厂商相同而合并。

- [ ] 在运维文档中固化“停调度 → 等待当前批次完成 → 同步定义 → 调整源视图 → 校验链路与映射 → 按生效策略处理预检 → 重建任务 → 启用调度”的流程。

验收：

## M3：数据校验与一致性

### [P0][VALID-001] 按配置执行校验方法

- [ ] `ROW_COUNT` 执行行数校验。
- [ ] `CHECKSUM` 对当前医共体数据集定义中的全部字段执行内容 Checksum。
- [ ] DFETL 内部维护的 `_etl_*` 字段不参与源目标 Checksum。
- [ ] 源端和 Doris 端按相同字段顺序及统一的空值、日期时间、数值和字符规范计算 Checksum。
- [ ] `ROW_COUNT_CHECKSUM` 先执行行数校验，再执行 Checksum。
- [ ] 校验结果记录实际使用的方法、字段范围、数据范围和数据版本。
- [ ] 与同步批次绑定的阻断型校验失败时，将当前执行批次标记为失败，水位保留为上一次成功提交值。
- [ ] 失败批次重试时使用原水位和原上界重新处理同一数据窗口。
- [ ] 不允许用行数相等替代 Checksum 成功。

验收：

- 构造源目标行数相同但医共体数据集字段内容不同时，Checksum 校验必须失败。
- 仅 `_etl_*` 内部维护字段不同时，Checksum 结果不受影响。
- 与同步批次绑定的校验失败时，该执行批次状态为失败，水位保持在上一次成功值。
- 重试失败批次不会跳过原增量窗口。

## 5. 待确认事项

### D-001：业务系统实例模型（已确认）

采用灵活的业务系统实例模型：

- 一个医共体可以有一套覆盖全部机构的区域 HIS。
- 一个医共体也可以有多套 HIS，每套覆盖不同的机构组合。
- 系统实例与机构、源数据源均采用多对多关系。
- 采集链路明确引用系统实例、源数据源和覆盖机构集合。
- 共享业务系统的同一源对象只建立一条链路，使用医疗机构代码区分多家机构。
- 医疗机构代码属于数据集联合主键的一部分。
- 厂商不是系统实例的唯一标识，也不是自动合并依据。

对应实施任务：`SRC-001`。

### D-002：数据集定义变化后的处理方式（已确认）

采用人工维护流程，不实现在线热更新和自动任务迁移：

- 已经运行中的同步批次允许完成，不立即取消。
- 重新同步数据集定义前，由管理员人工停用相关任务调度并确保不再启动新批次。
- 人工重新同步医共体数据集定义。
- 业务系统按新定义调整源视图。
- 人工重新校验采集链路结构和字段映射，并重新执行数据预检。
- 重新创建同步任务后再启用调度。
- 旧任务不自动修改、不自动迁移、不自动恢复；系统仅保留定义版本、任务快照和操作审计。

对应实施任务：`DATASET-001`。

### D-003：数据预检策略与三级继承（已确认）

预检不是系统硬编码的必经步骤，采用可配置三级继承模型：

- 配置层级为“全局默认 → 数据集覆盖 → 任务覆盖”；数据集和任务可选择继承上级。
- 最终模式为关闭（DISABLED）、提示（ADVISORY）、强制（REQUIRED）。
- 强制要求当前有效通过结果；提示只告警；关闭不检查预检结果。
- 任务创建复核、任务详情和每次运行记录必须显示最终生效模式及来源。
- 任务级覆盖和风险确认需要权限控制和审计，不另设隐式临时豁免。
- 链路、映射、源结构或数据集合同变化会使旧结果失效；仅强制模式因此阻断。
- 不预检会提高正式同步失败概率，这是使用者可选择的业务风险。
- 预检记录的 BLOCKER 是问题严重度，不等同于所有模式都必须拦截。
- 正式写入约束、最低联合业务主键契约和技术故障处理不被关闭。
- 上游策略更新如何影响已有任务，按 D-006 继续确认。

对应实施任务：PRECHECK-001、TASK-002、TASK-003、TEST-001、TEST-002。

### D-004：Reader 并发（已确认）

第一阶段固定单并发：

- 服务端 Reader 并发统一为 1。
- 前端不再提供可编辑的并发配置，避免界面配置与实际执行不一致。
- Fetch Size 仍可独立配置。
- 等主业务闭环稳定并完成真实性能评估后，再决定是否增加按稳定主键或时间范围分片的并发读取。

对应实施任务：`TASK-005`。

### D-005：Checksum 范围与批次失败语义（已确认）

- 首次全量执行必须完成严格校验；日常增量只校验本次数据窗口，另行安排定期全量治理校验。
- Checksum 覆盖当前版本医共体数据集定义中的全部字段。
- DFETL 为内部维护而新增的 `_etl_*` 字段不属于医共体数据集，不参与源目标 Checksum。
- 源端与 Doris 端必须使用相同字段顺序和统一的空值、日期时间、数值精度及字符规范，避免不同数据库表示差异造成误报。
- Checksum 可以按稳定规则分片计算和定位差异，但不得降级为只比较行数。
- 与同步批次绑定的阻断校验失败时，该执行批次直接判定为失败。
- 失败批次不提交新水位；任务保存的水位仍表示“上一次成功完成并通过校验的位置”，重试时据此重新处理原数据窗口。
- 独立的定期全量治理校验失败时，记录校验失败和告警，但不追溯修改已经成功提交的历史同步水位。

对应实施任务：`VALID-001`、`EXEC-001`、`TEST-003`.

### D-006：数据集策略更新对已有任务的影响

推荐：数据集策略是新任务默认值；已有任务保留快照并显示“数据集策略已有新版本”，由管理员选择对比并应用，避免自动修改生产任务。

需要确认：已有任务是人工应用更新，还是自动跟随数据集策略。

### D-007：无删除标识数据源的删除识别（已确认）

采用定期主键快照识别删除：

- 第一次完整提取建立有效基线。
- 后续完整快照与上一份有效快照比较，识别源端已经消失的业务主键。
- 快照失败或不完整时不替换有效基线。
- 第一阶段只形成删除差异，不自动删除 Doris 正式数据。
- 实际应用删除必须经过 dry-run、人工二次确认和审计。

对应实施任务：`VALID-005`。

### D-008：共享业务系统的多机构数据范围（已确认）

- 同一共享业务系统的源视图可以同时包含多家医疗机构数据。
- 标准数据集中的医疗机构代码属于联合业务主键的一部分。
- 同一系统实例、数据源、标准数据集和源对象只建立一条采集链路，不按机构复制相同链路和任务。
- 链路记录覆盖机构集合；机构代码用于数据归属、唯一性、预检问题定位、校验分组和统计下钻。
- 不同系统实例、不同数据源或不同源对象仍分别建立链路。

对应实施任务：`SRC-001`、`TASK-001`、`TASK-002`。

### D-009：源视图医疗机构代码（已确认）

- 源视图中的医疗机构代码始终与“机构管理”保存的机构编码完全一致。
- 机构编码在系统范围内全局唯一。
- 不维护厂商内部机构代码到标准机构编码的映射表，也不在“业务系统实例—覆盖机构”关系中增加源系统代码。
- 预检直接使用机构编码校验机构存在性、启用状态和链路覆盖范围。
- 空值、未知机构、停用机构或超出当前链路覆盖范围的机构代码均记录为阻断级问题；其是否阻止任务创建或运行由 D-003 的最终预检模式决定。
- 医疗机构代码继续作为标准数据集联合业务主键的一部分，用于唯一性、归属、预检定位、校验分组和统计下钻。

对应实施任务：`SRC-001`、`PRECHECK-001`、`TEST-001`。

### D-010：失败恢复、重新采集与数据补采（已确认）

DFETL 将三种操作定义为不同的业务命令：

1. **重试**
   - 默认用于普通任务失败。
   - 从最后成功检查点继续，保留已经提交到 Doris 的载入批次。
   - 例如 240 个载入批次在第 120 批失败时，从第 120 批恢复并继续至第 240 批，第 1～119 批不清理、不重复提交。
   - 重试完成且整次执行校验通过后，才提交新的业务水位。

2. **重新采集**
   - 从任务数据范围起点重新读取全部数据。
   - 默认使用 UPSERT 幂等覆盖，不清理目标表中已有记录。
   - 只有用户主动选择“清空重建”时才清理目标范围；必须展示影响范围、二次确认、校验权限并记录审计。
   - 共享目标表的清理必须限定当前链路或机构范围，禁止影响其他机构数据。

3. **数据补采**
   - 用于一个已经结束的历史时间窗口或主键范围，例如 `2026-08-01 00:00～12:00`。
   - 生成独立执行记录，保留补采条件和审计信息。
   - 不用于普通运行失败，不替代“重试”，也不修改主任务的失败检查点。

共同约束：

- 三种操作使用独立接口、权限点和审计事件。
- 按批次持久化检查点和 Doris Stream Load Label；恢复前先核实 Label 状态。
- 第一阶段 Reader 固定单并发，同时只允许一个在途写入批次，当前批次确认提交后才处理下一批。
- 三种操作都必须保证 UPSERT 幂等，并防止重复请求形成并发执行。

对应实施任务：`TASK-004`、`EXEC-001`、`TEST-002`。

### D-011：Doris 严格/宽松建表模式（已确认）

1. **严格模式**
   - 严格遵循医共体数据集定义，生成精确类型、长度、精度、联合主键和 NOT NULL。
   - 不符合定义的数据导致任务失败，不允许过滤异常记录后把任务判定成功。
   - 预检门禁不由严格模式硬编码，而是执行 D-003 的最终策略。
   - 提示或关闭预检可以直接运行，但目标约束错误会在正式写入阶段导致失败。
   - 源视图整改后通过“重试”从最后成功检查点恢复。

2. **宽松模式**
   - 基于 JDBC 元数据生成，采用 UNIQUE KEY Merge-on-Write。
   - 医疗机构代码和数据集联合业务主键必须非空并唯一。
   - 其余业务字段允许 NULL，并使用宽松类型承载源值。
   - 不执行一般字段的医共体格式、长度、非空和值域阻断。
   - 预检同样可配置为关闭、提示或强制。
   - 技术错误和最低主键契约错误仍导致失败。

3. **共同规则**
   - 建表模式和预检策略正交：前者决定目标结构与运行约束，后者决定运行前检查、提示或强制。
   - 系统提供能力和灵活配置，由使用者选择；系统不得静默改变选择或掩盖失败风险。
   - 模式写入目标表、链路和任务快照。
   - 两种模式均可启用行数和 Checksum，不允许静默丢行。
   - 模式切换必须评估和重建；涉及清理时二次确认并审计。
   - 同一目标表上的任务继承该表模式，不允许运行时临时切换。

对应实施任务：DORIS-001、PRECHECK-001、VALID-001、TEST-003。

## 6. 完成定义

一个任务只有同时满足以下条件才能勾选完成：

- 代码已提交并通过 JDK 21 编译。
- 数据库迁移可在空库和已有库验证。
- 前端调用真实接口，不以 Toast 代替状态更新。
- 成功、失败、加载、无权限和重试路径均已处理。
- 相关危险操作具有确认和审计。
- 文档说明配置、启动和验证方式。
- 主流程稳定前可暂缓接口测试，但必须记录验证步骤和测试补齐入口。
