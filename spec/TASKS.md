## 1. 项目目标

本阶段把已经迁移的 Java 服务和现有 Web 前端整合为可运行的 DFETL 系统，优先保证以下业务闭环：

1. 医共体数据定义同步为标准数据集。
2. 通过业务系统实例灵活组织数据源与覆盖机构，并为机构配置采集链路。
3. 基于有效采集链路和最终生效的预检策略创建同步任务。
4. 执行全量及增量数据同步，正确维护水位。
5. 按配置执行数据校验，校验未通过时按策略阻断水位推进。
6. 支持任务监控、问题诊断、告警、日志和审计。
7. 前端所有可见按钮均有明确、可验证的业务行为。

## 2. 业务边界

### 2.1 数据集

- 数据集以医共体数据模型为唯一来源。
- 数据集管理不提供手工新增、手工删除功能。
- 同步医共体定义时记录首次入库时间、最近同步时间、定义版本和合同 Hash。
- 数据集详情必须包含：
  - 基础信息
  - 字段结构
  - 同步策略
  - 数据校验
  - 消息通知
- 数据预检和数据校验等可继承策略采用“全局默认 → 数据集覆盖 → 任务覆盖”三级模型；消息通知只使用数据集级配置，不提供任务覆盖。任务运行记录保存实际生效值及来源。
- 治理类运行策略在任务选择“继承”时于下一批自动生效；读取、写入、水位、标准字段解析合同和转换合同的变更必须人工确认并生成任务新版本，详见 D-006。

### 2.2 业务系统实例

- “业务系统实例”表示医共体内实际部署的一套业务系统，不以厂商作为唯一标识。
- 同一厂商可以在一个医共体内部署多套独立系统实例。
- 一个业务系统实例可以覆盖全部机构，也可以只覆盖任意一组机构。
- 一个机构可以同时接入多套业务系统实例，例如 HIS、LIS、PACS，或处于迁移期的新旧两套 HIS。
- 业务系统实例与机构为多对多关系。
- 业务系统实例与源数据源为多对多关系：一套系统可跨多个数据库，一个数据库也可承载多个逻辑系统实例。
- 采集链路必须明确标准数据集、业务系统实例、源数据源、Schema 和源对象，并记录其覆盖的机构范围。
- 当一套共享业务系统的源对象包含多家机构数据时，以标准字段中的医疗机构代码区分机构；医疗机构代码必须参与联合业务主键。
- 源视图中的医疗机构代码必须与“机构管理”保存的机构编码完全一致，且机构编码全局唯一。
- 不建立厂商内部机构代码与标准机构编码之间的二次映射，也不在业务系统实例覆盖关系中增加“源系统机构代码”字段。
- 同一源对象不因覆盖多家机构而机械拆分成多条重复链路。
- 厂商、系统类型和版本用于描述、筛选和统计，不能作为自动合并系统实例的依据。

### 2.3 数据预检

- 数据预检与正式数据同步相互独立，仅由用户人工发起，不设置自动调度。
- 连接、对象、字段集合、类型和标准字段解析检查是预检第一阶段，不再提供独立结构校验功能。
- 预检只用于发现源视图的数据质量和结构问题，不写入正式业务表。
- 预检不保存或展示行级问题、业务主键明细和数据样例，只保留字段级和组合规则级汇总。
- 预检通过后，正式同步仍从源视图重新提取数据。
- 预检结果绑定采集链路版本、数据集合同 Hash 和源对象结构 Hash。
- 预检风险展示策略支持三级继承：全局默认 → 数据集覆盖 → 任务覆盖；数据集和任务均可选择“继承上级”。
- 缺少预检、预检有问题或结果过期时如实展示风险并记录审计，但一律不阻断任务创建或运行。
- 预检执行时检查医疗机构代码非空、存在、启用且属于当前链路覆盖范围，并按字段或组合规则汇总影响行数和实际偏差。
- 每次预检固定扫描整条采集链路，不提供单机构运行范围；汇总结果可按机构筛选和直接导出。
- 平台不自行划分警告或阻断等级；技术异常与完整执行后发现数据问题分别记录。
- 未执行预检时，正式 ODS 写入的最低技术契约和目标表约束仍然生效，遇到不合规数据时任务在运行阶段明确失败。

### 2.4 数据同步

- 同步任务必须来源于一条有效采集链路，并明确归属一个医疗机构和一个标准数据集，不允许绕过链路直接拼装源、目标配置。
- 同一医疗机构与同一标准数据集只允许存在一个未删除的同步任务；任务不保存生命周期状态，所有未删除任务均占用该唯一关系。
- 同步任务不覆盖多家机构；当共享源对象包含多家机构数据时，任务按自身医疗机构代码过滤读取。
- 标准任务按数据集合同生成固定组合：无业务主键使用 `FULL_ONLY + TRUNCATE + DUPLICATE_KEY`；有业务主键且有有效增量字段使用 `FULL_THEN_INCREMENT + UPSERT + UNIQUE_KEY`；有业务主键但无有效增量字段使用 `FULL_ONLY + UPSERT + UNIQUE_KEY`。
- 无业务主键任务每次读取当前机构全量；多个机构共用同一张 `ods_`，写入前只能清理当前机构的数据范围，禁止清空整张共享表。
- 当前机构的源端过滤和目标端清理使用数据集合同中的标准医疗机构代码字段及任务所属机构编码；`_etl_job_id` 只用于追踪，不能作为业务主键或唯一清理依据。
- 不自动生成 Hash、自增 ID 或 `row_number()` 作为替代业务主键。
- 任务运行前必须重新检查链路、数据源、目标源和任务快照，并按最终生效的预检策略处理预检结果。
- 数据集定义变更不做在线热更新，统一按人工维护流程处理。
- 水位只能在写入成功且阻断型校验通过后推进。
- DFETL 明确定义两种不同的数据读取操作，前端入口、服务端命令、权限、确认提示和审计记录不得混用：
  1. **重新采集**：用于普通任务失败后的人工恢复，也可由用户主动发起；从任务数据范围起点和第 1 批重新读取全部数据，不从历史成功批次续跑。默认使用 UPSERT 幂等覆盖目标表中已有记录，不主动清理数据；无业务主键任务先清理当前机构范围再全量写入。只有用户明确选择“清空重建”时才清理有业务主键任务的目标范围，并且必须二次确认、执行引用检查和记录审计。
  2. **数据补采**：针对一个已经结束的历史时间窗口或主键范围重新读取，例如补采 `2026-08-01 00:00～12:00`。数据补采是独立执行，不作为普通运行失败的恢复方式，不修改正常任务的正式水位。
- 每个载入批次必须记录真实游标、Doris Stream Load Label/事务状态和确认提交时间，但这些记录只表示本次执行进度，不作为下一次执行的恢复检查点。遇到响应不明确时先查询 Label 状态并回写 `load_batch`，不建立独立对账表。
- 第一阶段采用单 Reader、单个在途写入批次；只有当前批次确认提交成功后才读取并提交下一个批次。
- 示例：有真实联合业务主键的全量任务共 240 个载入批次，第 120 批失败时，第 1～119 批可能已经写入；人工“重新采集”仍从第 1 批重新读取至第 240 批，并通过 UPSERT 收敛。

### 2.5 数据校验

- 数据预检用于正式同步前的数据质量检查。
- 数据校验用于同步后核对源端与目标端一致性。
- 正式同步默认自动执行零容差 `ROW_COUNT`；核心数据由用户在数据集或任务策略中手工改为 `ROW_COUNT_CHECKSUM`，系统不自动判断核心数据范围。
- 默认 `lookbackHours=0`，首次全量、日常增量、有主键但无增量字段的全量 UPSERT、无主键机构范围清理重载，分别按本次同步使用的同一机构和同一数据范围校验。
- 默认关闭延迟自动复检，不在 30 秒后自动重跑；保留人工重新校验入口和独立运行记录。
- 校验方式必须严格执行任务配置，不能用行数校验替代 Checksum。
- 只有医共体数据集合同定义了真实业务主键时才能选择 `CHECKSUM` 或 `ROW_COUNT_CHECKSUM`；无业务主键数据集固定使用 `ROW_COUNT`，但仍可正常创建和运行同步任务。
- `splitPk`、机构代码、Hash、自增 ID、`row_number()` 等技术字段或假主键不能作为开放逐行内容校验的依据；前端应禁用不支持的方式，后端在保存策略时明确拒绝，不能拖到执行阶段再静默降级。
- Checksum 范围为当前版本医共体数据集定义中的全部字段；DFETL 内部新增的 `_etl_*` 维护字段不参与 Checksum。
- 为避免跨数据库表示差异造成误报，参与 Checksum 的字段必须按统一规则规范化空值、日期时间、数值精度、字符和字段顺序。
- 与同步批次绑定的最终生效校验通过后才能确认批次成功并推进水位；校验不一致、执行异常或无法完成时，该执行批次直接判定为失败，任务水位保留在上一次成功提交的位置。
- 全量校验、修改校验和删除校验分别保留独立的执行语义和历史记录。

### 2.6 Doris 表用途与固定存储合同

DFETL 不提供可配置的 `STRICT/PERMISSIVE` 正式建表模式。表用途由业务流程确定，并在 Doris 建表、读取、预检、正式写入和校验中执行固定合同：

1. **`ods_` 正式业务表**
   - 以当前版本医共体数据集定义为唯一目标结构。
   - 按标准字段生成精确 Doris 类型、长度、精度及 NOT NULL 约束；有业务主键时使用 `UNIQUE KEY`，无业务主键时使用 `DUPLICATE KEY`。
   - `L` 映射 Doris `BOOLEAN`，正式写入只接受 `0/1`；新标准 `B` 和历史 `BY` 统一映射 Doris `STRING`，内容使用标准 Base64 文本存储和校验。
   - 未知医共体类型或未知格式不得回退为 `VARCHAR(256)` 或其他兜底类型，必须增加显式、版本化映射；预检只展示该问题，不阻断任务创建，正式执行必须在写入前明确失败。
   - 违反标准格式、长度、精度、非空、主键或机构范围的记录不能作为成功批次静默跳过。
   - 未执行预检仍允许运行，但正式合同或目标约束错误会使任务在运行阶段失败。
   - 任一载入批次因数据质量问题失败时，任务失败并保留原水位，业务系统整改源视图后执行“重新采集”。

2. **`raw_` 数据预检表**
   - 固定用于数据预检，不是正式同步的另一种目标表模式。
   - 全部业务字段使用字符串类型并允许 `NULL`，原始值不转换、不截断、不修正。
   - 通过预检运行 ID 和采集链路 ID 隔离每次运行，仅用于结构和数据质量检查。
   - 正式同步不读取、发布或转换 `raw_` 数据，始终重新读取源视图并写入 `ods_`。
   - 预检进入终态后按已确认的 1 天保留策略清理原始数据。

共同边界：

- `ods_` 和 `raw_` 的用途及存储合同固定，不提供全局、数据集、采集链路或任务级修改，也不支持相互转换。
- 每个数据集在一个逻辑 Doris 部署中按固定命名得到一张 ODS 和一张 RAW；直接读取 Doris 实际元数据核对结构，不建立 PostgreSQL 表登记或结构版本表。
- 医共体数据集定义升级按版本化结构迁移处理，不视为表模式切换。
- 预检策略、行数和 Checksum 校验、消息通知及删除对账等治理配置不改变表的固定存储合同。
- `raw_` 只负责暴露问题；正式 `ods_` 写入必须如实执行医共体字段合同，不能使用预检表或兜底类型绕过。

## M1：核心领域模型整改

### [P0][SRC-001] 建立灵活的业务系统实例模型

现状：`SourceDataSource` 只有一个 `institutionId`，既不能表达一套区域 HIS 覆盖全部医疗机构，也不能表达医共体内多套 HIS 分别覆盖不同机构组的情况。

已确认模型：

- 一个部署及其独立 PostgreSQL 元数据库固定服务一个医共体；医共体名称和编码进入系统设置，不建立租户表或 `community_id`。
- 机构在 P0 中为扁平集合，不建立 `parent_id` 或层级继承。
- `business_system_instance`：表示实际部署的一套业务系统。
- `business_system_instance_institution`：维护系统实例与覆盖机构的多对多关系。
- `business_system_instance_datasource`：维护系统实例与源数据源的多对多关系；它是纯关联表，不保存用途或优先级。
- 源数据源支持 `HOST_PORT/JDBC_URL` 两种逻辑连接方式，凭据与 JDBC URL 分离；平台不管理第三方主备节点或自动故障切换。
- 目标 Doris 表示一个逻辑部署，支持单机或集群配置及一个或多个 FE 端点，不管理 BE 节点。
- 采集链路归属于业务系统实例和数据源，并记录覆盖机构集合；不再强制每家机构各建一条重复链路。
- 对共享源对象，采集链路可以覆盖多家机构；每个同步任务只选择其中一家机构，并按医疗机构代码过滤读取。

任务：

- [ ] 新增业务系统实例实体、接口、数据库迁移及启停状态。
- [ ] 实例属性至少包含：编码、名称、系统类型、厂商、版本、状态和说明。
- [ ] 支持一个实例覆盖全部机构或任意机构子集。
- [ ] 支持一个机构关联多套系统实例。
- [ ] 支持一个实例关联一个或多个源数据源。
- [ ] 支持同一源数据源承载一个或多个逻辑系统实例。
- [ ] 数据源与机构的可选范围通过系统实例关系计算，不再使用单一 `institutionId` 硬编码限制。
- [ ] 新建链路时依次选择系统实例、标准数据集、数据源、Schema 和源对象，并从系统实例覆盖范围内确认链路覆盖机构。
- [ ] 校验链路覆盖机构必须属于系统实例覆盖范围，所选数据源必须与实例有关联。
- [ ] 校验标准数据集中医疗机构代码字段存在、启用且属于联合主键。
- [ ] 源视图医疗机构代码直接使用机构主数据编码，不提供厂商内部代码映射实体、字段或配置入口。
- [ ] 同一系统实例、数据源、标准数据集和源对象组合只建立一条有效链路，避免按机构重复采集同一共享视图。
- [ ] 厂商仅作为实例属性；相同厂商的多套部署不得自动合并。
- [ ] 删除或停用实例前检查机构关联、数据源、链路和任务引用。
- [ ] 机构、数据源和链路列表展示对应系统实例及覆盖范围。

验收场景：

1. **全区域一套 HIS**：一个区域 HIS 实例关联县人民医院、县中医院、县妇保院和 9 家乡镇卫生院，可只关联一个共享数据源。
2. **多套 HIS 分组覆盖**：人民医院实例覆盖人民医院及部分乡镇；中医院实例覆盖中医院及部分乡镇；妇保院实例只覆盖妇保院，各实例使用自己的数据源。
3. **同机构多系统**：同一家机构可同时关联 HIS、LIS、PACS 等实例，采集链路按数据集选择正确实例和数据源。
4. **同厂商多实例**：同一厂商在不同机构组部署的两套 HIS 保持为两个独立实例。
5. **共享视图多机构采集**：同一源对象包含多家机构数据时，只建立一条覆盖对应机构集合的采集链路；为每家需要同步的机构分别建立单机构任务，任务按医疗机构代码过滤，预检、校验和统计可按链路汇总或按机构下钻。
6. **独立数据源/独立视图**：不同系统实例或不同源对象仍分别建立链路，不因厂商相同而合并。

### [P0][ROUTE-001] 统一标准字段到 JDBC 真实字段名解析

现状：路由校验、任务快照、Reader、预检和 Checksum 分别实现大小写匹配；额外字段仍只告警并忽略，部分源端过滤直接引用配置字段名，且遗留 `field_mappings` 暗示支持尚未端到端实现的字段重命名。

- [ ] 建立唯一的标准字段解析组件，输入当前版本数据集合同和 JDBC 元数据，输出只读解析快照。
- [ ] 标准字段与源字段只允许大小写差异；每个标准字段必须大小写不敏感地唯一命中。
- [ ] 源字段集合与标准字段集合必须完全相等，缺少或额外字段都形成明确结构错误。
- [ ] 大小写折叠后重名立即报错，禁止 `putIfAbsent` 后任选第一列继续。
- [ ] 不要求源字段物理顺序相同；Reader 按合同顺序显式投影。
- [ ] Reader、机构过滤、增量窗口、预检和 Checksum 全部复用同一解析快照，并在源端 SQL 中引用 JDBC 真实字段名。
- [ ] Doris 字段固定使用医共体标准字段小写名称。
- [ ] 删除标准业务路径中的字段重命名、默认值和转换表达式配置入口；不新增链路字段重命名实体。
- [ ] 任务版本只读保存解析快照及合同版本，用于执行和审计，不允许人工编辑。
- [ ] 将未知医共体类型/格式的版本化转换合同与源字段解析明确分离。

验收：

- 标准字段 `YILIAOJGDM` 可唯一解析 JDBC 字段 `yiliaojgdm` 或 `YiLiaoJgDm`，源端 SQL 使用真实名称，Doris 使用 `yiliaojgdm`。
- 任一字段缺少、额外或大小写折叠后重名时，预检结构阶段记录明确问题；正式执行在读取前明确失败，不静默忽略或改名。
- 字段顺序不同但名称集合完全相等时，Reader 按合同顺序正常投影。
- 页面只读展示解析结果，不存在字段重命名保存入口。

### [P0][TASK-001] 将任务身份从 JSON 提升为关系字段并保证任务唯一性

- [ ] 在同步任务表中增加 `institution_id`、`dataset_id`、`route_id` 等稳定关系字段；实例、源数据源和目标 Doris 通过链路版本取得，不在任务身份上重复保存。
- [ ] 每个同步任务只关联一个医疗机构和一个标准数据集，不保存多机构覆盖集合。
- [ ] 共享源对象包含多家机构时，将任务机构编码固化到任务版本，并作为源查询的必要过滤条件。
- [ ] 保留 JSON 快照用于审计，不再把它作为唯一查询依据。
- [ ] 建立“医疗机构 + 标准数据集 + 未删除”业务唯一约束；部署和数据库本身已经限定单一医共体。
- [ ] 所有未删除任务均占用唯一关系；只有逻辑删除旧任务后才释放。
- [ ] 任务不保存 `DRAFT/ENABLED/PAUSED/FAILED/DISABLED` 生命周期状态；“暂停/恢复任务”只修改用户控制的调度开关，最近执行结果和失败原因从执行记录查询，失败或取消均不自动暂停任务。
- [ ] 任务版本不保存 `DRAFT/PUBLISHED/SUPERSEDED` 状态；由 `current_version_id` 唯一确定当前版本，新版本插入和指针切换在同一事务完成。
- [ ] 创建任务时在事务内检查并发冲突，返回已存在任务的编号、名称、状态和跳转入口。
- [ ] 支持修改、暂停和版本升级已有任务，不通过创建第二个任务替代修改。
- [ ] 重新创建前必须删除旧任务；删除为逻辑删除，保留任务版本、批次、日志、水位、校验和审计记录。
- [ ] 存在运行中批次时不允许删除任务；必须等待完成或受控取消。
- [ ] 迁移已有任务数据并检测历史重复关系，重复数据不得静默覆盖。
- [ ] 路由、数据源和机构删除时检查引用关系。
- [ ] 解析旧 JSON 失败时给出可追踪错误，不能静默忽略。

验收：

- 同一医疗机构和标准数据集并发创建时只产生一个未删除任务。
- 原任务未删除时，无论任务是否暂停、最近一次执行是否失败，都仍占用“机构 + 数据集”唯一关系，不能另建重复任务；暂停后仍可人工运行原任务。
- 修改现有任务或生成新版本不改变任务身份，也不产生第二个任务。
- 逻辑删除旧任务后可以重新创建，旧任务历史仍可查询和审计。
- 同一共享采集链路可分别为不同机构创建任务，不需要计算任务机构范围交集。
- 可通过数据库关系准确查询数据集、链路、机构和任务。
- 删除链路不会产生孤儿任务。

### [P0][DATASET-001] 数据定义变更的人工维护流程

产品边界：

- 不支持在生产任务运行期间热更新数据集定义，也不自动迁移现有链路和任务。
- 数据集定义仅由管理员人工同步，不设置自动同步；只有规范化定义内容及 Hash 变化时才生成新版本。
- 数据集字段变更必须进入人工维护窗口。
- 已经运行中的同步批次允许完成，不自动取消。
- 管理员先暂停相关任务；第三方按最新定义调整源视图后，管理员再人工同步数据集定义。
- 人工重新核对链路结构和标准字段解析结果，并按需要执行预检，再显式生成新链路/任务版本或重建任务。
- 旧任务不自动套用新定义、不自动恢复；完成审计留痕后由管理员保持暂停或删除。

任务：

- [ ] 记录数据集首次入库时间、最近同步时间、定义版本、合同 Hash 和同步结果。
- [ ] 同步时先规范化定义并计算 Hash；内容未变化只更新同步时间和结果，不插入新版本。
- [ ] 定义同步结果展示字段新增、删除、类型和主键差异，但不自动修改现有任务。
- [ ] 执行定义同步前增加维护确认，明确提示先暂停相关任务并避免启动新批次。
- [ ] 任务快照保留创建时的数据集版本，用于历史批次和审计追溯。
- [ ] 新建任务只能使用当前数据集定义和当前标准字段解析结果；预检结果只用于展示事实和风险，不作为准入条件。
- [ ] 在运维文档中固化“暂停相关任务 → 等待当前批次完成 → 第三方调整源视图 → 人工同步定义 → 核对链路与字段解析 → 按需预检 → 人工生成新版本或重建任务 → 恢复任务”的流程。

验收：

- 字段变更维护期间，已经运行的批次能够正常完成且不会被系统自动取消。
- 系统不会自动修改、迁移或恢复旧任务。
- 重建后的任务使用最新数据集版本和重新解析的只读字段快照。
- 历史批次仍可追溯其使用的数据集版本和任务快照。

### [P1][DATASET-002] 数据集服务端分页和查询

- [ ] 支持编码、名称、业务分类、状态、更新时间筛选。
- [ ] 统计数量与实际数据一致。
- [ ] 避免读取全部字段、策略和链路后在内存过滤。

## M3：数据校验与一致性

### [P0][VALID-001] 按配置执行校验方法

- [ ] 全局正式同步默认启用自动校验，默认方法为零容差 `ROW_COUNT`，默认 `lookbackHours=0`。
- [ ] 核心数据允许用户通过数据集或任务策略手工覆盖为 `ROW_COUNT_CHECKSUM`，不维护系统自动识别核心数据的规则。
- [ ] 只有数据集合同存在真实业务主键时才允许 `CHECKSUM`/`ROW_COUNT_CHECKSUM`；无业务主键数据集固定使用 `ROW_COUNT`。
- [ ] 前端对无业务主键数据集禁用内容 Checksum 选项并显示“数据集没有业务主键，无法执行逐行内容校验”；数据集和任务策略保存接口执行同一校验。
- [ ] 逐行 Checksum 只使用合同业务主键，不接受仅有 `splitPk`、机构代码或生成的 Hash、自增 ID、`row_number()` 作为比对键。
- [ ] `ROW_COUNT` 执行行数校验。
- [ ] `CHECKSUM` 对当前医共体数据集定义中的全部字段执行内容 Checksum。
- [ ] DFETL 内部维护的 `_etl_*` 字段不参与源目标 Checksum。
- [ ] 源端和 Doris 端按相同字段顺序及统一的空值、日期时间、数值和字符规范计算 Checksum。
- [ ] `ROW_COUNT_CHECKSUM` 同时验证行数与全部业务字段 Checksum；不能因行数相等而跳过内容校验。
- [ ] 校验结果记录实际使用的方法、字段范围、数据范围和数据版本。
- [ ] 校验使用执行快照中当前机构和本批实际同步范围：首次全量及两类 `FULL_ONLY` 使用当前机构全量，日常增量使用当前机构本批真实增量窗口，不额外回看历史窗口。
- [ ] 与同步批次绑定的阻断型校验失败时，将当前执行批次标记为失败，水位保留为上一次成功提交值。
- [ ] 校验内部可分批计算，但 PostgreSQL 只在 `validation_run` 保存整次最终结果和 `difference_summary JSONB`；不建立 `validation_run_segment` 或 `validation_difference_summary`，失败后整次重新校验。
- [ ] 失败后重新采集使用新执行启动时固定的数据范围和上界，从任务范围起点完整处理；成功前不推进正式水位。
- [ ] 不允许用行数相等替代 Checksum 成功。

验收：

- 构造源目标行数相同但医共体数据集字段内容不同时，Checksum 校验必须失败。
- 仅 `_etl_*` 内部维护字段不同时，Checksum 结果不受影响。
- 与同步批次绑定的校验失败时，该执行批次状态为失败，水位保持在上一次成功值。
- 失败后的重新采集不会从失败批次继续，也不会在完整成功前推进正式水位。

依赖：已确认事项 D-005。

### [P0][DORIS-001] 实现 ODS/RAW 固定建表合同

- [ ] `ods_` 正式业务表使用医共体定义生成精确类型、长度、精度和 NOT NULL，并在标准定义业务主键时生成联合主键。
- [ ] 有业务主键的 `ods_` 使用 `UNIQUE KEY`；无业务主键的 `ods_` 使用 `DUPLICATE KEY`，不得生成假主键。
- [ ] 同一标准数据集的多个机构共用一张 `ods_`；无主键任务以标准医疗机构代码为条件清理当前机构旧数据后全量写入，禁止继续使用 `DROP_DATA` 清空整张物理表。
- [ ] 每个标准数据集在一个逻辑 Doris 部署中固定一张 `ods_` 和一张 `raw_`，表名由数据集编码和固定命名规则生成；链路和任务不能自由填写目标表。
- [ ] `raw_` 预检表的全部业务字段使用字符串类型并允许 `NULL`，原始值不转换、不截断、不修正。
- [ ] DDL 预览展示表用途、合同版本、字段来源、类型映射、键模型、分区和分桶，不提供模式选择。
- [ ] 删除全局、数据集、采集链路和任务中的 `STRICT/PERMISSIVE` 配置、覆盖和切换入口。
- [ ] 正式 ODS 写入不得跳过不合规记录后把批次标为成功。
- [ ] 正式 ODS 合同将 `L` 转换为只接受 `0/1` 的 Doris `BOOLEAN`，将新标准 `B` 与历史 `BY` 统一转换为标准 Base64 文本形式的 Doris `STRING`。
- [ ] 正式 ODS 合同遇到未知医共体类型或格式时不使用 `VARCHAR(256)` 等兜底映射；预检只提示，正式执行在写入前明确失败。
- [ ] 未预检任务若在正式写入遇到字段合同或目标约束错误，任务按真实结果失败。
- [ ] 不建立 PostgreSQL Doris 表登记或结构版本表；直接读取 Doris `information_schema.columns` 和 `SHOW CREATE TABLE`，与数据集版本生成的期望合同比较。
- [ ] 普通执行只校验 Doris 实际结构，不自动建表、加字段或修改结构；创建/重建只能由用户显式发起。
- [ ] 禁止 `ods_` 与 `raw_` 相互转换；医共体定义升级使用版本化结构迁移流程。
- [ ] 行数和 Checksum 传输一致性校验针对正式 ODS 写入执行，不复用 `raw_` 数据。

验收：

- `ods_` 始终按医共体合同建表和写入，预检结果不阻断任务创建或运行，不合规写入按真实结果失败。
- `L` 的合法 `0/1` 可写入，其他非空值失败；`B/BY` 按标准 Base64 文本写入；未知类型或格式不会通过兜底类型静默落库。
- `raw_` 的全部业务字段均为可空字符串，能够保留源端原始值并按预检运行隔离。
- 前端和接口均不存在正式表模式选择、覆盖或切换功能。
- 无主键任务的例行全量执行只替换当前机构数据，其他机构在同一张 `ods_` 中的数据保持不变。
- 表用途及合同版本只读可追溯，`raw_` 不会被转换或发布为 `ods_`。
- 医共体定义升级不会被实现为表模式切换。

- [ ] 只有配置启用的数据集发布消息。
- [ ] 发布范围固定等于本次成功同步范围：全量发送本次全量全部业务数据，增量发送本次增量全部业务数据；不实现 `ALL/SKIP/NOTIFY_ONLY`、完成通知或 TRUNCATE 信号，限速和分页大小正确执行。

## 4. 后续实施规划

### 4.1 总体执行原则

- 以 `spec/PRODUCT_AND_BUSINESS_DECISIONS.md` 为最终业务基线；本清单、历史 SQL、实体或迁移代码与其冲突时，先修正实现，不重新讨论已经确认的业务规则。
- 老系统继续连接原 `df_ygt/df_etl` PostgreSQL 数据库并正常运行；新系统只连接独立新库，开发期间不得修改、认领或升级老系统数据库。
- 先冻结新系统目标元数据模型，再编写 Flyway `V1`。不得把当前历史实体、老库 schema 或旧 `init.sql` 直接固化为新系统基线。

- 每个阶段的代码、SQL 和文档在同一次变更中维护；已在任一环境执行的 Flyway 版本不可修改，只能新增后续迁移或前向修复版本。

### D-001：业务系统实例模型（已确认）

采用灵活的业务系统实例模型：

- 一个部署及其独立 PostgreSQL 元数据库只服务一个医共体；医共体信息使用系统设置，不建立租户表。

- 系统实例与机构、源数据源均采用多对多关系。
- 实例与源数据源使用纯关联表，不保存用途或优先级，不自动选择或切换连接。

- 共享业务系统的同一源对象只建立一条链路，使用医疗机构代码区分多家机构。
- 医疗机构代码属于数据集联合主键的一部分。
- 厂商不是系统实例的唯一标识，也不是自动合并依据。

### D-002：数据集定义变化后的处理方式（已确认）

采用人工维护流程，不实现在线热更新和自动任务迁移：

- 已经运行中的同步批次允许完成，不立即取消。
- 管理员人工暂停相关任务并确保不再启动新批次。
- 第三方先按最新定义调整源视图。
- 管理员再人工同步医共体数据集定义；只有规范化内容及 Hash 变化才生成新版本，未变化只记录同步时间和结果。
- 人工重新核对采集链路结构和标准字段解析结果，并重新执行数据预检。
- 用户显式生成新链路/任务版本或重建同步任务后再恢复任务。
- 旧任务不自动修改、不自动迁移、不自动恢复；系统仅保留定义版本、任务快照和操作审计。

对应实施任务：`DATASET-001`。

### D-003：数据预检风险展示策略与三级继承（已确认）

预检仅由用户人工发起，不是任务创建或运行的准入门禁：

- 配置层级为“全局默认 → 数据集覆盖 → 任务覆盖”；数据集和任务可选择继承上级。
- 任务创建复核、任务详情和每次运行记录必须显示预检事实、风险、最终策略值及来源。
- 任务级覆盖和风险确认需要权限控制和审计。
- 链路、源对象、源结构或数据集合同变化会使旧结果失效，并展示过期风险，但不阻断任务创建或运行。
- 不预检会提高正式同步失败概率，这是使用者可选择的业务风险。
- 平台不为预检问题划分 WARNING/BLOCKER 等级，只保存字段级和组合规则级汇总。
- 正式写入约束、最低联合业务主键契约和技术故障处理不受预检是否执行影响。
- 上游策略更新按 D-006 的已确认规则处理：继承状态下从下一批开始生效，运行中批次保持原快照。

对应实施任务：PRECHECK-001、TASK-002、TASK-003、TEST-001、TEST-002。

### D-004：Reader 并发（已确认）

第一阶段固定单并发：

- 服务端 Reader 并发统一为 1。
- 前端不再提供可编辑的并发配置，避免界面配置与实际执行不一致。
- Fetch Size 仍可独立配置。
- 等主业务闭环稳定并完成真实性能评估后，再决定是否增加按稳定主键或时间范围分片的并发读取。

对应实施任务：`TASK-005`。

### D-005：Checksum 范围与批次失败语义（已确认）

- 首次全量执行必须完成本次最终生效的阻断校验；日常增量只校验本次数据窗口，另行安排定期全量治理校验。
- Checksum 覆盖当前版本医共体数据集定义中的全部字段。
- DFETL 为内部维护而新增的 `_etl_*` 字段不属于医共体数据集，不参与源目标 Checksum。
- 源端与 Doris 端必须使用相同字段顺序和统一的空值、日期时间、数值精度及字符规范，避免不同数据库表示差异造成误报。
- Checksum 可以在执行内部按稳定规则分批计算，但只在 `validation_run` 持久化整次最终结果和小型差异汇总 JSON；不得降级为只比较行数，也不提供分段恢复。
- 与同步批次绑定的阻断校验失败时，该执行批次直接判定为失败。
- 失败批次不提交新水位；任务保存的水位仍表示“上一次成功完成并通过校验的位置”。人工重新采集新建执行，并从任务数据范围起点完整读取。
- 独立的定期全量治理校验失败时，记录校验失败和告警，但不追溯修改已经成功提交的历史同步水位。

对应实施任务：`VALID-001`、`EXEC-001`、`TEST-003`.

### D-006：运行策略更新对已有任务的影响（已确认）

运行策略分为两类，不能统一采用同一种更新方式：

1. **可在下一批自动生效的治理类策略**
   - 数据预检提示和风险展示策略。
   - 数据校验方式：行数、Checksum 或组合方式。
   - 消息通知：只从数据集级策略读取是否启用及相关通知参数，不经过全局默认或任务覆盖层。
   - 当任务选择“继承”时，每个新批次启动前按“全局默认 → 数据集覆盖 → 任务覆盖”重新计算最终生效值。
   - 当任务明确配置任务级覆盖时，继续使用任务自己的配置，不跟随上级变化。
   - 已经运行中的批次始终使用启动时保存的运行快照，不受修改影响。
   - 每个新批次保存最终生效值、来源和策略版本，保证历史可追溯。

   上述继承和任务覆盖规则只适用于预检、校验等允许覆盖的策略；消息在新批次开始时直接读取数据集策略并保存快照。

2. **必须人工应用并生成任务新版本的执行类配置**
   - 写入模式、首次全量/后续增量方式。
   - 增量字段、增量模式、上界策略、回看窗口和初始水位。
   - 源对象、目标表、标准字段解析合同、转换合同和联合主键。
   - Reader/Writer、Fetch Size、过滤条件、分片、并发和其他影响读取范围或写入语义的参数。
   - 这些配置变化不能自动影响已有任务；管理员必须查看差异、确认影响并创建任务新版本。

3. **数据集定义变化不属于运行策略更新**
   - 字段新增、删除、类型、长度、格式或主键变化继续执行 D-002 的人工维护流程。
   - 需要调整源视图、重新核对链路和标准字段解析结果，并重建任务，不允许通过三级继承热更新已有任务。

系统界面要求：

- 任务详情显示“配置方式（继承/覆盖）”“当前生效值”“来源层级”和“生效策略版本”。
- 上级治理策略变化后，继承任务显示“将在下一批生效”；任务级覆盖显示“不受本次上级变更影响”。
- 策略变更、任务覆盖和任务新版本创建均写入操作审计。

对应实施任务：PRECHECK-001、TASK-002、TASK-003、VALID-001、MSG-001、TEST-002、TEST-003。

### D-007：无删除标识数据源的删除识别（已确认）

- 后续完整快照与上一份有效快照比较，识别源端已经消失的业务主键。
- 快照失败或不完整时不替换有效基线。

### D-008：共享业务系统的多机构数据范围（已确认）

- 同一共享业务系统的源视图可以同时包含多家医疗机构数据。
- 标准数据集中的医疗机构代码始终用于机构范围；数据集存在业务主键时，它与标准业务主键字段共同组成联合业务主键。
- 同一系统实例、数据源、标准数据集和源对象只建立一条采集链路，不按机构复制链路。
- 链路记录覆盖机构集合，用于限定可以基于该链路创建任务的机构。
- 同步任务不覆盖机构集合，每个任务只归属一家医疗机构和一个标准数据集。
- 同一共享链路可为不同机构分别创建任务；各任务按自身医疗机构代码过滤源数据。
- 不存在“一个任务覆盖多家机构”的场景，因此不设计任务机构范围交集检查。
- 不同系统实例、不同数据源或不同源对象仍分别建立链路。

对应实施任务：SRC-001、TASK-001、TASK-002。

- 医疗机构代码继续用于归属、机构范围过滤、预检定位、校验分组和统计下钻；数据集存在业务主键时，它同时参与联合业务主键；无业务主键时，它只限定机构范围，不单独冒充记录主键。

### D-010：重新采集与数据补采（已确认）

DFETL 将两种操作定义为不同的业务命令，不提供独立重试：

1. **重新采集**
   - 用于普通任务失败后的人工恢复，也可由用户主动发起。
   - 新建执行记录，从任务数据范围起点和第 1 批重新读取全部数据，不引用最后成功批次继续。
   - 例如 240 个载入批次在第 120 批失败时，新执行仍从第 1 批读取到第 240 批。
   - 默认使用 UPSERT 幂等覆盖，不清理目标表中已有记录。
   - 无业务主键时固定清理当前机构范围后全量重载。
   - 只有用户主动选择“清空重建”时才清理目标范围；必须展示影响范围、二次确认、校验权限并记录审计。
   - 共享目标表的清理必须限定当前链路或机构范围，禁止影响其他机构数据。
   - 完整写入且整次校验通过后，才提交新的业务水位。

2. **数据补采**
   - 用于一个已经结束的历史时间窗口或主键范围，例如 `2026-08-01 00:00～12:00`。
   - 生成独立执行记录，保留补采条件和审计信息。
   - 不用于普通运行失败，不替代“重新采集”，也不修改主任务正式水位。

共同约束：

- 两种操作使用独立接口、权限点和审计事件。
- 按批次持久化真实游标和 Doris Stream Load Label，但 `load_batch` 只表示单次执行进度；不建立检查点表，不保存重试来源或恢复批次字段。
- Doris 响应不明确时将 Label 探测结果回写 `load_batch` 并记录审计，不建立 `execution_reconciliation`；重新采集前核对旧 Label，避免旧批次仍可能提交时盲目重放。
- 第一阶段 Reader 固定单并发，同时只允许一个在途写入批次，当前批次确认提交后才处理下一批。
- 有业务主键的操作必须保证 UPSERT 幂等；无业务主键任务按当前机构范围清理后全量重载，不能退化为 APPEND。所有操作都必须防止重复请求形成并发执行。

对应实施任务：`TASK-004`、`EXEC-001`、`TEST-002`。

### D-011：Doris ODS/RAW 固定存储合同（已确认）

1. **`ods_` 正式业务表**
   - 固定遵循医共体数据集定义，生成精确类型、长度、精度和 NOT NULL；有业务主键时使用 `UNIQUE KEY`，无业务主键时使用 `DUPLICATE KEY`。
   - 同一标准数据集的多个机构共用一张 `ods_`；无业务主键任务每次只清理并重载当前机构范围，禁止整表 `TRUNCATE`/`DROP_DATA`。
   - `L` 映射 Doris `BOOLEAN` 且只接受 `0/1`；新标准 `B` 和历史 `BY` 统一映射 Doris `STRING` 并使用标准 Base64 文本。
   - 未知医共体类型或格式不得使用兜底类型，必须通过显式、版本化映射解决；预检只提示，正式执行在写入前明确失败。
   - 不符合定义的数据导致任务失败，不允许过滤异常记录后把任务判定成功。
   - 预检只展示事实和风险，不作为任务创建或运行门禁；未预检也可以直接运行。
   - 源视图整改后通过“重新采集”从任务范围起点重新读取。

2. **`raw_` 数据预检表**
   - 固定用于数据预检，全部业务字段使用字符串类型并允许 `NULL`。
   - 原始值不转换、不截断、不修正，并通过预检运行 ID 和采集链路 ID 隔离。
   - 不作为正式同步目标，也不向 `ods_` 发布或转换；正式同步始终重新读取源视图。
   - 终态数据按 1 天保留策略清理。

3. **共同规则**
   - 取消正式业务表的 `STRICT/PERMISSIVE` 可配置模式。
   - `ods_` 与 `raw_` 的用途和合同固定，不提供全局、数据集、采集链路或任务级修改，也不支持相互转换。
   - 每个数据集在一个逻辑 Doris 部署中按固定命名得到一张 ODS 和一张 RAW；系统直接核对 Doris 实际结构，不建立 PostgreSQL 表登记或结构版本表。
   - 医共体定义升级按版本化结构迁移处理，不视为模式切换。
   - 预检和校验策略仍可独立配置，但不能改变两类表的固定存储合同。

对应实施任务：DORIS-001、PRECHECK-001、VALID-001、TEST-003。


### D-012：同步任务唯一性与单机构归属（已确认）

- 同一医疗机构和同一标准数据集只允许存在一个未删除的同步任务；部署和数据库已经限定单一医共体。
- 每个同步任务只归属一个医疗机构，不存在单个任务覆盖多家机构的场景，也不需要检查任务机构范围是否重叠。
- 共享业务系统和共享源视图仍只建立一条采集链路；不同机构可以基于该链路分别创建自己的单机构任务。
- 单机构任务必须使用标准医疗机构代码过滤源数据。
- 所有未删除任务均占用唯一关系；任务不保存与执行结果和调度控制重复的生命周期状态。
- 已有任务可以修改、暂停或生成新版本；生成新版本仍属于原任务。
- 确需重新创建时，必须先逻辑删除旧任务后再创建新任务。
- 运行中任务不得删除；旧任务的版本、批次、日志、水位、校验和审计历史永久保留。
- 创建接口必须通过数据库唯一约束和事务处理并发请求，不能只依靠前端校验。

对应实施任务：TASK-001、TASK-002、TASK-004、TEST-002。

### D-013：标准任务类型与无主键机构范围清理（已确认）

1. **无业务主键**
   - 使用 `FULL_ONLY + TRUNCATE + DUPLICATE_KEY`，每次从源视图读取当前机构全量。
   - 多个机构共用同一张 `ods_`，任务执行时只清理当前机构已有数据，然后写入当前机构全量；禁止清空整张共享物理表。
   - 源端过滤和目标端清理都使用数据集合同中的标准医疗机构代码字段与任务所属机构编码。
   - `_etl_job_id` 只用于内部追踪，不能作为业务主键或唯一清理条件；系统不得生成 Hash、自增 ID、`row_number()` 等假主键。

2. **有业务主键且有有效增量字段**
   - 使用 `FULL_THEN_INCREMENT + UPSERT + UNIQUE_KEY`。
   - 首次执行读取当前机构全量，成功后提交初始水位；后续按增量窗口读取并按联合业务主键覆盖。

3. **有业务主键但没有有效增量字段**
   - 使用 `FULL_ONLY + UPSERT + UNIQUE_KEY`。
   - 每次读取当前机构全量并按联合业务主键覆盖，不在执行前清理目标数据。

4. **实现修正**
   - `MedicalRegistryController.preview-config` 必须按实际主键和增量字段生成预览，不能无条件显示 `UNIQUE_KEY + UPSERT + XIUGAISJ`。
   - `SeaTunnelConfBuilder` 的无主键标准任务不能继续使用作用于整张物理表的 `data_save_mode=DROP_DATA`；必须实现当前机构范围的安全清理和全量写入。
   - `SharedTargetTableGuard` 从“共享表一律禁止 TRUNCATE”调整为“禁止整表破坏操作，并校验机构范围清理条件准确且只影响当前机构”。

对应实施任务：TASK-002、TASK-003、TASK-004、DORIS-001、EXEC-001、TEST-002、TEST-003。

### D-014：正式同步默认校验策略（已确认）

- 正式同步默认自动执行零容差 `ROW_COUNT`；平台不自动判断核心数据，核心数据由用户在数据集或任务策略中手工改为 `ROW_COUNT_CHECKSUM`。
- `ROW_COUNT_CHECKSUM` 必须同时验证本次范围内的行数与全部业务字段内容，不能因缺少比对键、数据量或性能原因静默降级为 `ROW_COUNT`。
- 默认 `lookbackHours=0`。校验使用与本次同步完全相同的机构和数据范围：首次全量及两类 `FULL_ONLY` 校验当前机构本次全量，日常增量校验当前机构本批真实增量窗口。
- 最终生效的校验通过后才能确认批次成功、推进正式水位并进入消息发布；不一致、异常或无法完成均按失败收尾。
- 取消默认 30 秒自动复检及其他固定延迟自动复检；保留人工重新校验入口，每次重新校验生成独立运行记录并关联原同步执行。
- 校验方法继续遵循“全局默认、数据集覆盖、任务覆盖”，最终生效值固化到任务版本和执行快照。

对应实施任务：VALID-001、VALID-002、VALID-003、VALID-004、EXEC-001、MSG-001、TEST-003。

### D-015：无业务主键数据集的校验能力（已确认）

- 只有当前版本医共体数据集合同定义了真实业务主键时，才能选择 `CHECKSUM` 或 `ROW_COUNT_CHECKSUM`。
- 无业务主键数据集固定使用默认的 `ROW_COUNT`；这不阻断任务创建和正式同步。
- 前端将内容 Checksum 选项置为不可选，并明确显示“数据集没有业务主键，无法执行逐行内容校验”。
- 数据集和任务校验策略保存接口必须拒绝无业务主键与内容 Checksum 的组合；不能保存后在执行阶段静默降级。
- `splitPk` 只可承担技术分片职责，机构代码只可承担机构范围职责；两者以及 Hash、自增 ID、`row_number()` 均不能伪装成业务主键。
- 未来确有无主键内容校验需求时，新增显式、版本化的“整体内容 Checksum”协议；该能力只判断整体一致性，不混入当前 `ROW_COUNT_CHECKSUM` 的逐行业务键对齐语义。

对应实施任务：VALID-001、VALID-002、WEB-006、TEST-003。

### D-016：标准任务源对象与 CUSTOM_SQL 边界（已确认）

- 标准医共体同步任务只支持稳定的表、视图或物化视图，不支持在 DFETL 中直接配置 `CUSTOM_SQL`。
- 需要关联、过滤、计算或转换时，由源系统建立并维护视图；预检、同步、增量和校验始终围绕同一个版本化源对象执行。
- 任务创建页面删除自定义 SQL 入口，标准任务创建和更新接口拒绝 `sourceMode=CUSTOM_SQL`。
- 移除标准业务路径中的自定义 SQL 校验、字段探测、预览、执行及特殊兼容逻辑，避免形成只支持行数、不支持完整 Checksum 的半成品能力。
- 当前没有历史 `CUSTOM_SQL` 任务，不需要兼容、自动改写、数据迁移或历史任务转换流程。
- 将来确有非标准自由查询同步需求时，作为独立产品能力重新设计 SQL 解析、数据库强制只读、资源治理、版本、增量和校验合同，不混入标准任务。

对应实施任务：SRC-001、TASK-002、TASK-003、VALID-001、WEB-003、WEB-004、TEST-002、TEST-003。

### D-017：标准字段大小写解析与禁止重命名（已确认）

- 标准字段与源字段只允许大小写差异；不支持别名、人工重命名、默认值或转换表达式改变字段身份。
- 每个标准字段必须在 JDBC 元数据中按大小写不敏感方式唯一命中。
- 源字段集合与标准字段集合必须完全相等；缺少或额外字段都形成明确结构错误。
- 源字段按大小写折叠后重名时立即报错，不能选择其中一个继续。
- 源字段物理顺序不要求与标准定义相同；Reader 按合同顺序显式投影。
- Reader、机构过滤、增量窗口、预检和 Checksum 共用同一个“标准字段 → JDBC 真实字段名”解析结果；所有源端 SQL 使用真实字段名按源库方言引用。
- Doris 业务字段固定使用标准字段的小写名称。
- 系统仅在任务版本中只读保存字段解析快照和合同版本，不提供全局、数据集、链路或任务级字段重命名入口。
- 未知医共体类型或格式的显式版本化映射属于字段转换合同，与源字段重命名无关。

对应实施任务：ROUTE-001、TASK-002、PRECHECK-001、VALID-001、TEST-002、TEST-003。

### D-018：新旧系统隔离与数据库迁移基线（已确认）

- 老项目连接原 `df_ygt/df_etl` 数据库持续运行，直到新项目完整验收并正式替换；新项目不改造、不接管老数据库。
- 新项目使用独立的全新 PostgreSQL 数据库，从 Flyway `V1__baseline.sql` 开始，不与老项目共享 Quartz、任务、执行、校验、水位或消息状态。
- 老库 schema-only 导出是历史结构证据，不是新系统 V1；不得重放旧 `init.sql` 和历史 `migration_*.sql`，也不得给老库写 Flyway baseline 标记。
- 新系统 V1 按最终业务基线和新实体模型重新建立；后续每次结构或基础数据变化都新增不可变 Flyway 版本，并同步维护检查、验证和回退/前向修复说明。
- 最终替换阶段单独确定需要迁移的配置；旧执行历史、Quartz 状态和废止模型默认不自动迁移。

对应实施任务：DB-001、DB-002、CFG-001、OPS-001。

### D-019：P0 目标元数据模型第一批 Review（已确认）

- 单个部署只服务一个医共体；医共体名称和编码进入系统设置，不建立 `medical_community` 或业务表 `community_id`。
- 机构 P0 不建层级；`business_system_instance_datasource` 是纯关联表。源连接支持 `HOST_PORT/JDBC_URL`，目标 Doris 支持单机/集群逻辑部署。
- `collection_route` 只用 `deleted_at` 表示逻辑删除，不保存状态；已有未删除任务引用时禁止删除。
- 每个数据集在一个逻辑 Doris 部署中固定一张 ODS 和一张 RAW。平台直接读取 Doris 实际元数据，不建立表登记或结构版本表；普通执行不得自动改表。
- 数据集只人工同步且仅在定义内容变化时生成版本。平台不自动迁移链路、Doris 或任务，也不自动重启和恢复任务。
- 保留精简的 `collection_route_version`，只在规范化定义内容变化时生成；重复核对不生成版本。
- 删除 `sync_task.lifecycle_status` 和 `sync_task_version.status`；调度控制、执行结果和当前版本指针分别表达。
- 删除 `sync_task.schedule_blocked` 和 `block_reason`；失败原因从执行记录查询，失败不自动修改用户控制的 `schedule_enabled`。
- 删除 `sync_task.catch_up_pending`；重叠计划调度直接跳过，不建立补跑状态。
- 删除 `task_watermark_history`；只保留当前正式水位，推进和人工重置分别由执行记录与 `audit_log` 追溯。
- 删除 `sync_execution.recollect_of_execution_id`；执行表不建立重新采集自关联。
- 删除 `validation_run_segment`；校验内部可分批计算，但不持久化分段状态或提供分段恢复。
- 删除 `validation_run.recheck_of_run_id`；人工重新校验是独立运行，同一同步执行允许产生多次人工重新校验记录。
- 删除 `validation_difference_summary`；小型差异汇总直接保存到 `validation_run.difference_summary JSONB`。
- 删除 `message_delivery_attempt`；消息重试、死信和人工重发状态全部收敛到 `message_outbox`。
- 删除 `message_outbox` 的 `FAILED` 状态；可重试失败复用 `PENDING`，并以 `available_at` 表示下一次允许投递时间。
- 删除 `message_outbox.next_attempt_at`；首次发送、失败重试和人工重发统一更新 `available_at`，发布扫描使用 `(status, available_at)` 索引。
- `message_outbox` 每次执行只保存一条小型发布指令，不保存业务数据；发布器从 Doris 分页读取，失败后整段重发，不建立分页进度、分页明细或逐条消息表。
- 消息重发不保存原执行业务数据的历史快照；增量按原批次或窗口、全量按当前任务机构范围读取当前 Doris，允许后续 UPSERT 使重发内容与原执行不同或减少。
- P0 不设置 `message_outbox` 自动清理、归档任务或保留期；`PUBLISHED/DEAD_LETTER` 长期保留，任务逻辑删除不级联删除历史记录，后续需要时另行设计。
- `messageKey` 模板和空值处理沿用旧协议：缺失或 `NULL` 占位字段替换为空字符串并继续发送；`messageId` 继续使用 27 位时间戳、机器标识和序号组合，每次发送重新生成，不改为确定性 ID。
- 删除 `message_outbox.provider_message_id`；整段发布只保存汇总状态、次数、时间和最后错误，逐条提供方消息标识写应用日志。
- `PUBLISHING` 异常恢复复用 `last_attempt_at` 和全局超时参数；不建立发布租约表或工作节点归属字段，恢复仅改变 Outbox 状态。
- 删除 Redis Stream 传输路径和消息 transport 字段，只保留 RabbitMQ。
- 删除按任务复制的 `MessagePublishConfig` 和任务级消息覆盖；消息策略按数据集唯一，任务/执行只提供机构、Doris 目标、批次和窗口等运行上下文并保存当次快照。
- 删除 `message_outbox.event_type`，对 `execution_id` 建唯一约束，一次执行只创建一条发布指令。
- RabbitMQ Exchange 固定为 `YL` 并由平台幂等声明，连接参数留在部署配置；数据库仅保存数据集级 Routing Key、Topic 和消息业务参数。
- 删除数据集和任务消息配置中的 `full_sync_mode`、`send_truncate_signal` 以及 `FULL_SYNC_COMPLETE`/TRUNCATE 信号分支；发布范围始终与本次同步范围一致。
- 取消执行不修改 `schedule_enabled`；暂停/恢复任务是独立操作，只控制后续自动调度。
- 预检固定扫描整条链路；汇总可按机构筛选并直接导出 XLSX/CSV，不导出详情，不建立预检或校验异步导出任务表。
- 删除 `execution_checkpoint` 和 `execution_reconciliation` 表；不保留独立重试、`retry_of_execution_id` 或 `resume_from_batch_id`。普通失败后只允许人工重新采集并从第 1 批读取。

本项只更新阶段 1 文档，不创建或固化 Flyway `V1__baseline.sql`。目标模型其余部分继续逐项 Review。

对应实施任务：SRC-001、DATASET-001、ROUTE-001、TASK-001、PRECHECK-002、DORIS-001、EXEC-001、DB-001。

### D-020：简单管理员账号与成功/失败操作审计（已确认）

- 系统可只配置一个管理员账号，也可按实际使用人数配置多个同权限管理员账号；不设置人数硬限制，通常为 1～3 人。
- P0 不建设 RBAC，不建立角色、权限及其关联表，也不提供菜单、按钮、API 或数据范围权限配置。
- “系统设置”提供简单账号管理：账号列表、新增、启停和重置密码；账号不提供物理删除入口。
- 当前登录账号不能停用自己，最后一个启用账号不能停用；停用或重置密码后撤销该账号既有 Refresh Token。
- Flyway 和初始化 SQL 不写入固定管理员密码或固定生产密码 Hash。
- 所有业务写操作同时审计成功和失败，记录本地账号、外部 API client、调度器或系统任务等操作者类型，以及 `WEB/EXTERNAL_API/SCHEDULER/SYSTEM` 等来源。
- 审计使用受控操作编码，保存目标类型、目标 ID、目标名称快照、`SUCCESS/FAILED` 结果、请求关联标识、客户端 IP 和小型脱敏摘要。
- 失败审计保存业务错误码和脱敏后的错误摘要；密码、密码 Hash、数据库密码、RabbitMQ 凭据、外部 API secret 和签名原文不得进入审计或普通应用日志。
- 普通只读查询默认不写业务审计；登录失败、无效 Token、HMAC 签名失败等认证事件进入安全日志。
- `audit_log` 只追加，不提供普通修改、删除、审批、处理状态或明细子表。

对应实施任务：`SEC-001`、`WEB-006`、`DB-001`。

### D-021：最小告警历史与最低实施优先级（已确认）

- 告警渠道、规则、规则启停、渠道测试、静默窗口和 Webhook 发送继续保留。
- 每次告警规则实际命中生成一条 `alert_event`，保存规则和严重程度快照、来源对象、关联任务/执行/预检/校验标识、标题、摘要和触发时间。
- 同一告警事件向每个目标渠道发送时，各生成一条 `alert_delivery`，保存渠道快照、发送状态、汇总尝试次数、最后尝试时间、成功时间和脱敏错误摘要。
- 一个渠道发送失败不影响其他渠道继续发送，也不影响同步任务和校验的业务状态。
- 不建立告警确认、认领、处理人、处理状态流转、工单或审批流程。
- 不建立逐次发送重试明细表，不长期保存完整 Webhook 请求或响应载荷；详细过程写应用日志。
- 告警中的 Webhook URL、签名密钥和敏感响应内容不得进入事件摘要、投递错误或操作审计。
- 告警功能实施优先级最低：排在数据同步、预检、校验、消息、外部 API 和基础运维能力之后，但仍属于最终交付范围。

对应实施任务：`OPS-001`、`DB-001`、`WEB-006`。

## 6. 完成定义

一个任务只有同时满足以下条件才能勾选完成：

- 代码已提交并通过 JDK 21 编译。
- 数据库迁移可在新系统空库和新系统上一正式版本数据库验证；老系统数据库不得作为 Flyway 升级目标。
- 前端调用真实接口，不以 Toast 代替状态更新。
- 成功、失败、加载、无权限和对应人工恢复路径均已处理。
- 相关危险操作具有确认和审计。
- 文档说明配置、启动和验证方式。
- 主流程稳定前可暂缓接口测试，但必须记录验证步骤和测试补齐入口。
