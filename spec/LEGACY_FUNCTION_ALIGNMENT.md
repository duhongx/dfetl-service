# 老系统功能与新系统目标范围对齐

> 状态：阶段 1 功能边界对齐基线  
> 对齐日期：2026-08-14  
> 老系统代码基线：`duhongx/datax-lite-jdk21@175a15ff6d7f1f3b258a0422420ea672610933a4`（`master`）  
> 新系统文档基线：`duhongx/dfetl-service@341e3b5d070e5b2a242457c74d325ca7639c43d4`（`main`）  
> 最终业务基线：`spec/PRODUCT_AND_BUSINESS_DECISIONS.md`

## 1. 对齐规则

本文件用于防止两类错误：一是只看老代码而把已明确废止的功能重新带入新系统；二是只看新模型而漏掉老系统仍在使用、且新文档没有明确删除的业务能力。

统一采用以下判断顺序：

1. `spec/PRODUCT_AND_BUSINESS_DECISIONS.md` 是最终业务基线。
2. `datax-lite-jdk21/master` 当前可达的 Controller、Service、Repository、前端路由和菜单用于确认老系统实际具备的功能；历史 Spec、失效文档、孤立实体或不可达代码不能单独证明功能仍需保留。
3. 老系统实际功能如果已被新文档明确删除或改变，按新文档执行，不保留旧实现兼容分支。
4. 老系统实际功能如果新文档没有明确删除，默认保留其业务能力；允许按新领域模型、事务边界和安全规则重写实现。
5. 新系统不复制老表和旧状态机。功能保留不等于表名、字段、默认值、接口内部参数或实现类原样迁移。
6. 只有同时具备“实际代码/调用路径证据”和“与新业务基线的明确冲突或模型缺口”时，才记为问题；不得根据可能性虚构业务需求。
7. 老代码文档与当前代码不一致时，以当前可达代码为老功能事实源。

## 2. 处置分类

| 分类 | 含义 |
| --- | --- |
| 保留 | 老功能和新业务语义一致，继续提供。 |
| 重构保留 | 业务能力继续提供，但必须按新模型重写，旧表、状态或接口内部实现不继承。 |
| 明确删除 | 新文档已经明确移除，新系统不再提供。 |
| 合并替代 | 老系统存在多个重叠入口或对象，新系统以一个统一领域能力承接。 |
| 历史实现残留 | 当前主业务路径不可达，不能仅因实体、Repository 或历史 SQL 存在就进入新模型。 |
| 待补齐 | 老系统有实际能力且新业务基线仍要求，但当前目标模型尚未完整表达。 |

### 3.11 外部任务 API

老系统当前可达代码的业务输入以医疗机构编码和标准数据集编码为核心：


`requestId`、`runAfterCreate` 和 `failurePolicy` 是幂等、是否立即运行及批量失败处理控制，不是数据源、源对象、同步、校验或消息业务策略。

## 4. 已明确删除的旧前端入口

新产品文档已明确删除以下入口，对应旧页面、路由、Controller 或实体不得因为代码仍存在而重新进入新系统：

- 任务中心“批量模板”；
- 运维管理“机构数据视图”；
- 独立“结构校验”；
- 旧的不可达数据预检抽屉；
- 没有入口的链路运行记录面板；
- 行级脏数据、行级差异和自动修复相关页面。

数据预检从旧“数据校验”分组移动到“任务中心”，与“数据同步”“任务监控”并列；这属于信息架构调整，不是删除预检功能。

## 5. 当前发现的真实文档/模型缺口

### 5.1 使用文档入口被最终导航清单漏列

老系统有真实 `/docs` 前端页面、菜单和 `/api/docs/**` 后端接口，新业务文档没有明确删除。按本文件对齐规则，该功能应保留；需要在 `PRODUCT_AND_BUSINESS_DECISIONS.md` 最终导航和后续 Web 任务中补列，而不是静默删除。

### 5.2 删除识别的持久化模型尚未完整表达

业务基线已确认定期主键快照、有效基线、失败快照不替换基线、差集预览、dry-run 和人工应用。当前目标模型只有通用 `validation_run`，未明确大量主键快照存放位置、有效基线指针、差集生命周期和应用记录。该缺口会直接影响删除识别能否实现，必须在目标模型 Review 中单独补齐。

### 5.3 外部 API 的老文档与当前代码不一致

`docs/external-sync-task-api.md` 仍描述较早的源对象和策略参数，而当前实际 DTO 已收敛为机构、数据集及少量技术控制字段。新系统应以当前可达代码确认老功能边界，并以新领域模型重写，不使用失效文档扩展参数。

### 5.4 外部 API 限流不是已实现的老功能

当前目标模型把“限流状态”与老功能并列，但老代码和历史 SQL没有对应实现证据。后续必须把“老功能迁移”和“新增安全增强”分开描述，避免把不存在的旧能力当成迁移缺口。

## 6. 后续 Review 使用方式
