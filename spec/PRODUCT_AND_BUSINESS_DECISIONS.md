> 项目：`duhongx/dfetl-service`  
> 目标分支：`main`  
> 首次整理：2026-08-13  
> 最近更新：2026-08-14  
> 文档性质：本会话已确认需求、业务规则、产品边界、前端交互要求与实施任务的统一基线。

## 1. 项目目标与边界

DFETL 是面向医共体的数据采集与传输平台，负责把 PostgreSQL、MySQL、Oracle、SQL Server 等业务系统中的视图或表数据同步到 Doris。

一个 DFETL 部署及其独立 PostgreSQL 元数据库固定服务一个医共体。医共体名称和编码作为系统设置保存，不建立租户表，也不在业务表重复保存租户 ID。当前机构按扁平集合管理，不设计父子层级。

系统提供数据源、标准数据集、采集链路、数据预检、数据同步、同步后校验、消息通知、任务监控和运维能力。平台应提供灵活、透明、可追溯的配置能力，不替使用者作业务决策，不通过隐式限制或静默纠错掩盖数据问题。

当前阶段目标：

1. 将 `datax-lite-jdk21/master` 中 Java 生产代码迁入 `dfetl-service/main`；已删除的 `master-2` 不再作为核对基线。
2. 暂不迁移测试代码；主业务流程跑通后再补接口测试。
3. 对迁移代码开展业务 Review，重点覆盖数据集管理、任务创建、任务执行、数据预检和数据校验。
4. 将 Web 从高保真 Mock 原型完善为行为完整、可路由、可持久化的商业系统前端。
5. 以本文件和仓库任务清单作为后续开发与验收基线。

## 2. 核心术语

| 术语 | 定义 |
| --- | --- |
| 医共体 | 当前系统的业务租户/管理范围，包含多家医疗机构。 |
| 医疗机构 | 县人民医院、县中医院、县妇保院、乡镇卫生院等独立机构；机构编码全局唯一。 |
| 业务系统实例 | 医共体内真实部署的一套 HIS、LIS、PACS 等系统，关联厂商、系统类型、数据源及其覆盖机构。 |
| 源数据源 | 第三方提供的 PostgreSQL、MySQL、Oracle、SQL Server 等逻辑数据库连接，支持主机端口或完整 JDBC URL 两种配置方式。 |
| 目标数据源 | 一个逻辑 Doris 部署及其连接、写入参数，支持单机或集群配置。 |
| 标准数据集 | 从医共体数据模型同步而来的数据定义，不允许在数据集管理中手工新增。 |
| 采集链路 | 标准数据集与业务系统实例、源数据源、Schema、源对象、目标数据源及标准字段解析合同之间的配置关系。 |
| 数据同步任务 | 基于采集链路建立的长期任务；一个任务只归属一家医疗机构和一个标准数据集。 |
| 执行 | 同步任务的一次实际运行。 |
| 载入批次 | 一次执行内按游标范围拆分的 Doris Stream Load 单元。 |
| 正式水位 | 最近一次完整成功且校验通过的增量边界。 |
| 数据预检 | 上线前或人工发起的源数据全量核查能力，使用 `raw_` 临时表，不写入正式 ODS。 |
| 数据校验 | 正式同步后对源端实际同步载荷与 Doris 结果的一致性核对。 |

## 3. 核心领域模型

### 3.1 业务系统实例

采用灵活的“业务系统实例”模型，不以厂商或单个机构作为实例唯一边界。

必须支持：

- 一个区域 HIS 覆盖医共体内全部机构，并共用一个数据源。
- 人民医院及部分乡镇一套 HIS、中医院及部分乡镇一套 HIS、妇保院一套 HIS。
- 同一家机构同时关联 HIS、LIS、PACS 等多个系统实例。
- 同一厂商部署多套相互独立的系统实例。
- 一个系统实例关联多个数据源；一个数据源承载多个逻辑系统实例。
- 业务系统实例与医疗机构为多对多关系。
- 业务系统实例与源数据源为多对多关系。

厂商、系统类型、版本只用于描述、筛选和统计，不作为自动合并依据。

业务系统实例与源数据源的关系是纯关联关系，不配置用途或优先级，平台不自动选择、切换或故障转移源端连接。源数据源使用 `HOST_PORT` 或 `JDBC_URL` 方式配置，凭据单独保存，不嵌入 JDBC URL。目标 Doris 以逻辑部署配置，支持单机或集群的一个或多个 FE 端点，不管理 BE 节点。

### 3.2 机构代码

- 源视图中的医疗机构代码必须与机构管理中的机构编码完全一致。
- 不增加厂商内部机构代码映射。
- 医疗机构代码是所有正式数据集的机构范围字段；数据集存在业务主键时，医疗机构代码与标准业务主键字段共同组成联合业务主键。数据集没有业务主键时，医疗机构代码只用于机构归属、过滤和范围清理，不得被单独冒充记录主键。
- 共享视图可包含多家机构数据，任务按自身机构代码过滤读取。

### 3.3 采集链路和任务的机构范围

- 同一系统实例、数据源、数据集和源对象只建立一条采集链路，链路可以覆盖多家机构。
- 不因共享视图包含多家机构而重复建立相同链路。
- 同一共享链路可以分别为不同机构建立单机构同步任务。
- 一个同步任务不覆盖多家机构，因此不设计任务机构范围交集检查。
- 预检、校验和统计可按链路汇总，并按机构下钻。

## 4. 标准数据集管理

### 4.1 数据来源和生命周期

- 标准数据集只能由管理员从医共体数据模型人工同步，不允许手工新增，也不设置自动同步。
- 记录首次入库时间、最近同步时间、同步结果、定义版本和定义 Hash。
- 只有规范化定义内容及定义 Hash 发生变化时才生成新的不可变版本；内容未变化时只更新同步时间和结果。
- 数据集详情保留五个核心分区：基础信息、字段结构、同步策略、数据校验、消息通知。
- 数据集列表重点展示数据集本身，不在主表堆叠覆盖机构、采集链路状态、任务状态和最近同步等无关信息。
- 采集链路在数据集行下展开管理，数据集与链路职责分离。

### 4.2 数据集定义发生变化

数据集定义变化采用人工维护流程，不做在线热更新：

1. 管理员人工暂停相关任务；已经运行中的批次允许按原快照完成。
2. 第三方先按医共体最新定义修改其源视图。
3. 管理员在 DFETL 中人工同步最新数据集定义；只有定义内容变化才生成新的不可变数据集版本。
4. 人工核对采集链路、源对象实际结构和标准字段解析结果，并按需要重新执行数据预检。
5. 用户显式创建新的链路版本和任务版本，或重建任务，然后恢复任务。

新数据集版本发布后，旧链路版本和旧任务版本继续引用原数据集版本。平台只提示存在待人工应用的新版本，不自动迁移链路、不自动修改 Doris、不自动切换任务版本，也不自动重启或恢复任务。

### 4.3 字段转换合同

`ods_` 正式业务表中，医共体字段定义必须由同一个“字段合同转换器”统一服务于：

- Doris DDL 生成；
- Reader 取值与转换；
- 数据预检规则；
- Checksum 规范化。

依据 `datax-lite-jdk21/master` 当前代码确认的主要规则：

- `AN`、`A` 等字符串格式按声明长度映射，考虑 UTF-8 字节容量；现有代码通常使用 `声明长度 × 3` 生成 `VARCHAR`。
- 超长普通字符串可映射为 `STRING`；业务主键必须使用有界可索引类型，不允许无界 `STRING`。
- `N` 格式解析精度和小数位；无小数时按范围选择 `INT`、`BIGINT` 或 `DECIMAL`，有小数使用 `DECIMAL(precision, scale)`。
- `D/D8` 映射 `DATE`；`DT/D8/DT15` 等时间格式映射 `DATETIME(6)`。
- `L` 映射 Doris `BOOLEAN`；正式 ODS 写入只接受 `0/1`，字段允许为空时仍按统一可空规则接受实际 `NULL`。
- 新标准 `B` 和历史 `BY` 统一视为二进制类型，映射 Doris `STRING`，内容使用标准 Base64 文本存储和校验。
- 未知医共体类型或未知格式在正式 ODS 合同中不得回退为 `VARCHAR(256)` 或其他兜底类型，必须通过显式、版本化的字段转换合同解决。预检只展示未知合同问题，不阻断任务创建；正式执行必须在写入前明确失败，不能按兜底类型静默写入。

需要修复的代码不一致：

1. Doris 正式建表与模型预览/预建表必须使用同一套生成器；不能一个保留非主键 `NOT NULL`，另一个把非主键全部改成 `NULL`。
2. 可空字段只允许实际值为 `NULL`；只要实际值非空，仍必须检查类型、长度、格式、精度和值域。现有代码仅对主键或非空字段执行部分数值/时间检查，需要修正。
3. 医共体标准字段转换与“源数据库类型到 Doris 类型”的通用映射是两套不同合同，不得混用。

## 5. 采集链路

### 5.1 链路内容

采集链路必须明确：

- 标准数据集；
- 业务系统实例；
- 源数据源；
- 源 Schema；
- 源表、视图或物化视图；
- 目标 Doris 逻辑数据源；目标数据库来自数据源配置，ODS/RAW 表名由标准数据集编码和固定命名规则确定，不允许自由填写；
- 覆盖机构；
- 标准字段解析合同及只读解析快照；
- 当前配置版本。链路版本只在数据集版本、源对象、目标 Doris、覆盖机构或字段解析快照等规范化定义内容变化时生成；重复核对且内容未变化时不生成版本。

标准医共体链路不提供源字段重命名映射。字段解析固定遵循以下规则：

1. 标准字段与源字段只允许大小写差异，不接受别名、人工重命名、默认值或转换表达式改变字段身份。
2. 每个标准字段必须在 JDBC 元数据中按大小写不敏感方式唯一命中。
3. 源字段集合与标准字段集合必须完全相等；缺少或额外字段都形成明确结构错误。
4. 源字段按大小写折叠后重名时立即报错，不能任选一个字段继续。
5. 不要求源字段物理顺序与标准定义相同；Reader 必须按合同顺序显式投影。
6. 机构过滤、增量窗口、正式 Reader、数据预检和 Checksum 等全部源端 SQL，共用同一个“标准字段 → JDBC 真实字段名”解析结果，并使用真实字段名按源库方言引用。
7. Doris 业务字段固定使用医共体标准字段的小写名称。
8. 系统只读保存解析结果用于任务版本和审计，不提供全局、数据集、链路或任务级字段重命名入口。

未知医共体字段类型或格式所需的“显式、版本化映射”仅指字段类型/格式转换合同，不是源字段重命名能力。

标准医共体任务不支持在 DFETL 内直接编写 `CUSTOM_SQL`。需要关联、过滤、计算或转换时，由源系统提供稳定的表、视图或物化视图，并将该源对象作为采集链路和任务版本的一部分。当前不存在历史 `CUSTOM_SQL` 任务，因此不设计兼容、自动改写或迁移流程。

### 5.2 链路操作

采集链路本身不执行，不显示“运行状态/最近同步”。操作包括：

- 配置链路；
- 进入“数据同步”，携带 `datasetId`、`linkId/routeId` 和 `institutionId` 并自动过滤；
- 进入“数据预检”，携带相同上下文并自动过滤；
- 删除链路。

删除为危险操作，必须二次确认、检查引用并记录审计。已有未删除任务引用时不得产生孤儿关系。

### 5.3 Doris 实际表核对

每个标准数据集在一个逻辑 Doris 部署中固定共用一张 ODS 和一张 RAW，多家机构使用标准机构编码隔离。PostgreSQL 不建立 Doris 表登记表或结构版本表。

平台直接读取 Doris 的实际列信息和建表语句，并与当前不可变数据集版本生成的期望结构比较。普通同步执行只校验，不自动建表、补字段或修改 Doris；建表和重建只能由用户显式发起，并统一使用字段合同 DDL 生成器。

### 5.4 连接与结构检查

取消独立的“结构校验”产品功能。连接、对象、字段集合、类型和标准字段解析检查并入数据预检第一阶段。

最终确认：

- 结构或预检结果不作为创建任务和运行任务的硬性准入条件。
- 平台展示风险和事实，允许用户按权限继续操作。
- 正式执行遇到真实结构或数据错误时，任务明确失败并通知维护人员。
- 不做虚假的自动修复、自动迁移或猜测性判断。

## 6. 同步任务模型与创建

### 6.1 唯一性

- 同一医疗机构、同一标准数据集只能存在一个未删除同步任务；部署和数据库本身已经限定单一医共体。
- 所有未删除任务均占用唯一关系。
- 任务不保存与执行结果重复的生命周期状态。自动调度是否启用只由用户控制的调度开关表达；“暂停任务”设置 `schedule_enabled=false`，“恢复任务”设置为 `true`。暂停后仍允许人工运行。
- 可以修改调度控制，也可以为同一任务生成新的不可变版本。
- 如需重新创建，必须先逻辑删除旧任务。
- 运行中的任务不得删除；历史版本、批次、日志、水位、校验和审计保留。
- 唯一性由数据库约束和事务共同保证，不能只在前端判断。

### 6.2 任务创建向导

建议三步：

1. 选择业务系统实例、采集链路、医疗机构和标准数据集。
2. 展示源目标配置、标准字段解析结果、当前预检结果和风险；所有问题只提示，不作为硬性门禁。
3. 复核任务名、写入、全量/增量、调度、校验、消息、字段和水位策略。

向导最终提交时一次性创建任务和第一个不可变版本，不长期保存任务或版本草稿。任务必须保存当时的数据集版本、标准字段解析结果和执行配置快照。当前版本由任务的 `current_version_id` 指针确定，历史版本不再重复保存 `PUBLISHED/SUPERSEDED` 状态。

## 7. 策略继承与版本

采用“全局默认 → 数据集覆盖 → 任务覆盖”三级配置。

### 7.1 下一批可自动生效

任务处于“继承”时，下列治理策略在下一批开始前重新计算：

- 数据预检提示/风险展示策略；
- 数据校验方式；
- 消息通知。

任务明确覆盖时继续使用任务值。运行中批次不受修改影响。每次执行保存最终生效值、来源层级和策略版本。

### 7.2 必须生成任务新版本

以下执行合同变化不得热更新：

- 写入模式；
- 全量/增量方式；
- 增量字段和水位；
- 源对象、目标表；
- 标准字段解析合同和转换合同；
- 联合业务主键；
- Fetch Size、过滤条件、分片等改变读取或写入语义的参数。

数据集字段定义变化不属于普通策略变化，执行第 4.2 节人工流程。

### 7.3 标准数据集任务类型

标准数据集任务根据当前版本医共体字段合同固定生成以下组合，不生成 Hash、自增 ID、`row_number()` 等替代业务主键：

1. **无业务主键：每次全量清理重载**
   - 任务使用 `FULL_ONLY + TRUNCATE + DUPLICATE_KEY`。
   - 每次从源视图读取当前机构的全部数据。
   - 多个机构共用同一张 `ods_` 表，写入前只清理当前任务所属机构的数据范围，禁止清空整张共享物理表。
   - 清理条件使用数据集合同中的标准医疗机构代码字段和任务所属机构编码；`_etl_job_id` 只用于追踪，不能作为唯一范围依据或业务主键。
2. **有业务主键且有有效增量字段：首次全量、后续增量**
   - 任务使用 `FULL_THEN_INCREMENT + UPSERT + UNIQUE_KEY`。
   - 第一次执行读取当前机构全量，成功后提交初始水位；后续按增量窗口读取并按联合业务主键覆盖。
3. **有业务主键但没有有效增量字段：每次全量 UPSERT**
   - 任务使用 `FULL_ONLY + UPSERT + UNIQUE_KEY`。
   - 每次读取当前机构全量并按联合业务主键覆盖，不在运行前清理已有数据。

标准任务不使用 `APPEND` 作为上述三类任务的默认写入语义。任务类型、主键和增量字段属于执行合同，变化时生成任务新版本。

## 8. 调度、增量窗口与任务重叠

### 8.1 默认调度

- 全局默认每 4 小时执行一次增量。
- 4 小时只是调度周期，不是固定数据窗口。
- 默认自动错峰，避免大量任务同时启动。
- 数据集和任务均可覆盖默认周期。
- 每次执行保存最终生效的调度和增量策略快照。
- 正常任务的执行时长应明显短于调度周期；如果接近或超过当前周期，由维护人员把该任务周期调整为 12 小时或更长。

### 8.2 禁止并发和跳过重叠触发

- 同一任务禁止并发执行。
- 当前执行未结束时到达新的计划调度触发，直接跳过并记录日志，不创建待运行或待追赶状态。
- 当前执行完成后不为被跳过的调度立即补跑；等待下一次计划调度。
- 当前执行失败后直接记录失败并告警，不自动恢复或自动重新采集，也不暂停后续自动调度。
- 下一次计划调度照常运行。维护人员根据告警自行决定是否暂停任务、调整调度周期或人工重新采集。
- 普通失败只提供人工“重新采集”，不提供从失败批次继续的独立重试能力。

### 8.3 增量字段和时间范围

- `XIUGAISJ` 是业务方指定的增量字段。
- 默认不回看，避免重复读取；保留可配置回看窗口用于特殊数据源。
- 默认上界延迟 5 分钟。
- 每次执行启动时按源数据库时间计算 `upper = current_time - upper_delay`，本次执行内保持固定。
- 增量范围统一采用左闭右开区间 `[watermark, upper)`。
- 执行成功后正式水位推进到 `upper`；下一次执行重新计算上界。
- 空窗口成功也推进水位。
- 迟到数据不自动回扫，通过人工数据补采解决；补采不改变正式水位。
- 时间由统一时间服务器保证，不另行设计复杂的跨系统时钟补偿。
- `task_watermark` 只保存当前正式水位和最后成功执行，不建立单独的水位历史表。
- 正常水位推进从成功 `sync_execution` 保存的固定下界、上界和结果追溯；人工重置水位的前后值、原因和操作者写入通用 `audit_log`。

### 8.4 首次全量后的补充增量

- 首次全量开始时间作为初始增量水位。
- 全量完成后立即执行一次补充增量，覆盖全量执行期间产生的变化。它属于首次全量流程，不是对重叠计划调度的补跑。

## 9. 大表读取、载入批次与幂等

### 9.1 游标分页

- 有业务主键的全量使用“联合业务主键”游标分页。
- 增量使用“`XIUGAISJ` + 联合业务主键”游标分页。
- 无业务主键的 `FULL_ONLY` 任务使用单 Reader 流式全量读取，不使用 `OFFSET`，也不生成假主键；正式写入前只清理当前机构的数据范围。
- 禁止使用 `OFFSET`。
- 第一阶段 Reader 固定单并发。
- 每个载入批次持久化实际可用的主键/时间/机构范围、确认提交时间和 Doris Label。
- `load_batch` 只记录本次执行的批次进度、范围和 Doris 最终状态，不作为下一次执行的恢复检查点；不建立 `execution_checkpoint` 表，也不保存 `resume_from_batch_id`。
- 执行失败后发起“重新采集”时，一律从任务数据范围起点和第 1 批重新读取；无业务主键时先清理当前机构范围再全量执行。

### 9.2 确定性 Label

- 每个载入批次使用可重复推导的确定性 Doris Stream Load Label。
- 客户端超时或返回不明确时，先查询 Doris 的 Label/事务最终状态。
- Label 探测结果直接保存在 `load_batch` 并记录审计，不建立独立的执行对账表；重新采集前先核对旧 Label，禁止在旧批次仍可能提交时盲目重发。

### 9.3 失败后重新采集

本节的 UPSERT 收敛规则适用于有联合业务主键的任务；无业务主键任务固定采用当前机构范围清理后全量重载，不得套用假主键或 APPEND 恢复。

一次执行可能由数百个载入批次组成。例如 1,200 万行按 5 万行拆分约 240 批：

- 第 120 批失败时，第 1～119 批可能已经提交到 ODS。
- 第 120～240 批尚未完成。
- 正式水位仍停留在本次执行开始前。
- 人工发起“重新采集”后，从第 1 批重新读取到第 240 批；有业务主键时通过 UPSERT 收敛，无业务主键时清理当前机构范围后全量重载。

正式水位只在本次重新采集完整写入且校验通过后推进。平台不提供从第 120 批继续的独立重试，以减少检查点、恢复关联和分支状态的复杂度。

## 10. 失败、取消与两种人工操作

### 10.1 失败规则

- 遇到连接、结构、数据、写入或校验异常，执行直接失败。
- 不自动重试。
- 失败只产生告警和消息通知，不修改 `schedule_enabled`，下一次计划调度仍可创建新的执行。
- 维护人员根据失败原因自行决定暂停任务、等待下一次调度或发起重新采集。
- 失败不推进正式水位。

### 10.2 重新采集

- 用于普通运行失败后的人工恢复，也可由用户主动发起。
- 新建独立执行记录，从任务数据范围起点和第 1 批重新读取，不从历史成功批次续跑。
- 执行只以 `operation_type=RECOLLECT` 标识，不保存指向历史执行的自关联；发起入口、原因和操作者写入通用 `audit_log`。
- 默认使用 UPSERT 幂等覆盖，不清理已存在目标数据。
- 无业务主键任务先清理当前机构范围，再全量写入。
- 只有用户明确选择“清空重建”才清理目标范围。
- 清空重建必须展示影响范围、二次确认、权限校验和操作审计。
- 重新采集完整写入且整次校验通过后才推进正式水位。

### 10.3 数据补采

- 针对已结束的历史时间窗口或主键范围重新读取。
- 不用于普通失败恢复。
- 生成独立执行记录。
- 不修改主任务正式水位。

### 10.4 取消运行

取消执行采用以下确定流程：

1. 停止后续读取和载入。
2. 核实正在提交载入批次的 Doris 最终状态。
3. 保留已经提交的数据。
4. 不推进正式水位。
5. 标记当前执行为已取消。
6. 不修改任务调度开关，下一次计划调度照常运行。

“取消执行”只作用于当前执行；需要停止后续自动调度时，维护人员另行执行“暂停任务”。

## 11. 同步后校验与 Checksum

### 11.1 默认策略与覆盖

- 正式同步默认在写入完成后自动执行 `ROW_COUNT`，默认行数容差为 0。
- 核心数据可由用户在数据集或任务策略中手工改为 `ROW_COUNT_CHECKSUM`；系统不得自行判断或自动升级哪些数据属于核心数据。
- `ROW_COUNT` 只比较本次校验范围内的源端和 Doris 行数；`ROW_COUNT_CHECKSUM` 同时核对行数和全部业务字段内容，行数相等不能替代 Checksum 通过。
- 校验方式沿用“全局默认、数据集覆盖、任务覆盖”的最终生效规则，并保存到任务版本及执行快照。
- 默认 `lookbackHours=0`，校验范围不得向本批实际同步范围之前扩展。
- 默认关闭自动复检，不在 30 秒或其他固定延迟后自动重复校验；保留人工重新校验能力和独立执行记录。
- 人工重新校验以 `trigger_type=MANUAL_RECHECK` 标识，不保存指向历史校验运行的自关联；原同步执行、数据范围和任务版本仍按本次运行快照明确记录，操作者和发起入口进入 `audit_log`。
- 本次最终生效的阻断校验通过后，才能确认执行批次成功、推进正式水位并进入后续消息发布；校验不一致、校验异常或无法完成时均不得以同步成功收尾。
- 配置为 `ROW_COUNT_CHECKSUM` 时不得因缺少比对键、数据量或性能原因静默降级为 `ROW_COUNT`；不满足执行条件时必须明确失败并说明原因。
- 只有当前版本医共体数据集合同定义了真实业务主键时，才能选择 `CHECKSUM` 或 `ROW_COUNT_CHECKSUM`；`splitPk`、机构代码及其他技术字段不能代替业务主键取得逐行内容校验能力。
- 无业务主键的数据集固定使用 `ROW_COUNT`。前端将内容 Checksum 方式置为不可选并说明原因，后端在策略保存阶段拒绝不支持的组合；这不阻断任务创建和按 `ROW_COUNT` 执行正式同步。
- 不得为内容校验生成 Hash、自增 ID、`row_number()` 或其他假主键。未来如需校验无主键数据集的内容，应新增显式、版本化的“整体内容 Checksum”协议，不改变现有 `ROW_COUNT_CHECKSUM` 的逐行业务键对齐语义。

### 11.2 范围

- 校验使用与本次同步完全相同的机构范围和数据范围。
- 首次全量执行校验当前机构本次全量。
- 日常增量只校验当前机构本批实际增量窗口。
- 有业务主键但无有效增量字段的 `FULL_ONLY + UPSERT` 任务，每次校验当前机构本次全量。
- 无业务主键的 `FULL_ONLY + TRUNCATE` 任务，每次校验清理并重载后的当前机构全量。
- 另行提供定期全量治理校验。
- Checksum 覆盖当前数据集定义中的全部业务字段。
- DFETL 内部 `_etl_*` 字段不参与 Checksum。

### 11.3 计算方式

- 源端 Checksum 基于读取和转换过程中产生的实际同步载荷计算，不在同步完成后重新查询源视图。
- Doris 端按内部执行/载入批次标识核对相同载荷范围。
- 源端和 Doris 端共用同一套规范化协议。
- 基于转换后的实际业务字段计算。
- `NULL`、空字符串和仅空格字符串严格区分。
- 数值和日期时间按数据集定义统一规范。
- 字段顺序固定。
- 执行/批次保存 Checksum 协议版本。
- 本次最终生效的阻断校验通过后才确认执行成功并推进正式水位。

### 11.4 重复主键

- 本节只适用于定义了联合业务主键的数据集。
- 联合业务主键重复属于源端数据质量问题。
- 数据预检输出组合规则问题汇总。
- 正式同步不自动去重。
- 通过执行级行数和 Checksum 识别同批或跨批重复；发现后执行失败且不推进水位。

## 12. 删除对账

删除同步独立为“删除对账”，不随每 4 小时增量执行：

- 模式：关闭、仅检测、自动删除。
- 默认：仅检测。
- 默认周期：每周一次；删除频繁的数据集可配置每天一次。
- 支持手工执行。
- 支持全局默认、数据集覆盖、任务覆盖。
- 每次执行保存最终生效策略快照。
- 无删除标识的数据源使用联合业务主键快照识别源端删除。
- 无业务主键的 `FULL_ONLY + TRUNCATE` 数据集不执行主键快照删除对账；每次全量任务通过清理并重载当前机构范围，自然移除该机构已从源视图消失的数据。
- 不完整或失败的快照不得替换上一份有效基线。
- 自动删除必须设置数量和比例防护，并进行权限校验、二次确认和审计。

## 13. 消息通知

- 当前只有 3 个数据集启用消息，其他数据集默认关闭。
- 关闭的消息配置不在列表中制造噪音，但数据集详情必须保留重新开启入口。
- 业务消息只在整次同步和校验成功、正式水位推进完成后发布。
- 消息发送与同步事务解耦。
- 消息发送失败不改变同步成功状态。
- 每次执行使用唯一事件 ID，保证重发幂等。
- 消息可靠性只维护一条 `message_outbox`：保存投递次数、最后尝试时间、最后错误、提供方消息 ID 和最终状态；不建立逐次投递明细表，每次尝试的详细过程写应用日志。
- Outbox 状态只使用 `PENDING/PUBLISHING/PUBLISHED/DEAD_LETTER`，不设置 `FAILED`：临时失败回到 `PENDING` 并设置下次重试时间，达到最大次数进入 `DEAD_LETTER`，人工重发再回到 `PENDING`。
- 配置字段沿用原代码中的来源系统、租户 ID、Routing Key、Topic、messageKey 模板、首次全量模式、限速和分页大小。

## 14. 数据预检

### 14.1 定位

- 数据预检放在“任务中心”下，与“数据同步”“任务监控”并列。
- 数据预检是上线前或问题排查时由人工启动的核查能力，不设置自动调度。
- 每次预检固定扫描整条采集链路覆盖的源视图，不提供只运行某一家机构的模式；结果仍按机构汇总和筛选。
- 是否后续再次执行由用户决定，平台只保证核查能力和结果准确。
- 数据预检不作为任务创建或运行的准入条件。
- 不提供独立结构校验；结构检查是预检第一阶段。
- 不提供样例预览 Tab；样例不能代表预检结果。

### 14.2 执行阶段

1. 检查数据源连接、源对象存在性、字段集合、类型和标准字段解析结果。
2. 有真实联合业务主键时使用游标分页全量扫描；无业务主键时使用单 Reader 流式全量扫描，不生成假游标。
3. 原样载入 `raw_` 临时表。
4. 按医共体定义执行类型、长度、格式、非空、值域和组合主键规则检查。
5. 生成字段级和组合规则级汇总。
6. 进入终态后按保留策略清理本次 `raw_` 数据。

### 14.3 `raw_` 临时表

- 每个标准数据集共用一张 `raw_` 预检表。
- 通过预检运行 ID 和采集链路 ID 隔离每次运行。
- 全部业务字段使用字符串类型并允许 `NULL`。
- 原始值不转换、不截断、不修正。
- 正式同步不复用 `raw_` 数据，仍从源视图重新读取。
- 重新预检创建新运行，不覆盖历史。
- 终态后保留本次原始数据 1 天，由定时任务清理。
- 长期只保存运行记录和问题汇总。

### 14.4 状态

执行状态和结果状态分开：

- 执行状态：待运行、提取中、校验中、已完成、失败、已取消。
- 结果状态：通过、有问题。
- 只有技术异常标记为失败。
- 完整执行后发现不合格数据标记为“已完成、有问题”。
- 平台不自行划分警告或阻断等级。

同一采集链路同一时间只允许一个预检运行。不同链路的并行数量由全局参数控制。

### 14.5 输出内容

不保存和展示行级问题明细，不保存业务主键级明细，也不展示数据样例。

页面按当前筛选条件直接生成 XLSX/CSV 汇总表，不导出行级详情或样例，不建立异步导出任务表或长期文件存储。

报告必须让核查人员清楚知道：

- 哪个标准数据集；
- 哪个采集链路/机构；
- 哪个字段或联合主键规则；
- 违反了哪项医共体定义；
- 影响多少行；
- 实际偏差情况，例如实际最大长度、非法格式数量、空值数量、超范围情况或重复组合数量。

预检的目的，是让核查人员定位“哪些列不符合定义”并通知业务视图维护方整改，而不是在平台中处理逐行脏数据。

## 15. Doris 表用途与固定存储合同

### 15.1 `ods_` 正式业务表

- 固定严格遵循任务版本所绑定的医共体数据集版本，不提供可配置的严格/宽松模式。
- 生成精确类型、长度、精度和 `NOT NULL`；有业务主键的数据集使用 `UNIQUE KEY`，无业务主键的数据集使用 `DUPLICATE KEY`。
- 同一标准数据集的多个机构共用同一张 `ods_` 表；无业务主键任务的例行全量清理只能作用于当前机构，禁止使用整表 `TRUNCATE`/`DROP_DATA`。
- 任何载入批次遇到不合规数据均失败，不静默过滤异常行。
- 未知字段类型或格式必须先补充显式、版本化映射，不能使用兜底类型写入。
- 业务系统整改源视图后由人工重新采集。

### 15.2 `raw_` 数据预检表

- 固定用于数据预检，不是正式同步的宽松目标表。
- 全部业务字段使用字符串类型并允许 `NULL`，原始值不转换、不截断、不修正。
- 通过预检运行 ID 和采集链路 ID 隔离数据，仅供结构和数据质量检查。
- 不从 `raw_` 向 `ods_` 发布或转换；正式同步始终重新读取源视图。
- 按预检保留策略清理，不作为长期业务数据保存。

### 15.3 固定边界

- `ods_` 和 `raw_` 的用途及存储合同由业务流程固定，不提供全局、数据集、采集链路或任务级修改。
- 两类表不支持相互转换；不得把 `raw_` 提升为正式业务表，也不得把 `ods_` 降级为预检表。
- 每个数据集在一个逻辑 Doris 部署中按固定命名得到一张 ODS 和一张 RAW。系统直接读取 Doris 实际元数据并与任务绑定的数据集版本比较，不建立 PostgreSQL 表登记或结构版本表。
- 医共体数据集定义变化后，由用户显式执行 Doris 建表或重建能力并人工生成新链路/任务版本；平台不自动改表或切换任务。
- 预检是否执行以及行数/Checksum 校验、消息通知、删除对账等治理能力仍可独立配置，不改变表的固定存储合同。

首页以运行态势为主，不放“管理采集链路”等管理按钮，不堆砌解释文案。

建议展示：

- 接入机构、标准数据集、采集链路和待处理异常的核心数量；
- 今日同步数据量与执行趋势；
- 今日任务成功、运行中、失败分布；
- 机构接入健康度；
- 待处理异常及可下钻入口；
- 最近任务。

页面标题不重复展示“首页/数据采集总览/医共体名称”等无实际信息增量的文案。

### 16.3 数据源管理

- 源数据源和目标数据源使用页签。
- 新建按钮放在页签对应筛选区右侧，文案随页签变化。
- 源数据源支持 PostgreSQL、MySQL、Oracle、SQL Server 等联动表单；MySQL 不展示 Schema 概念。
- 源数据源列表展示数据库/Schema、用户名和掩码密码，不展示无意义“权限”列。
- 目标 Doris 不提供“环境标识”。
- Doris 参数包括 FE 地址、FE 端口、HTTP API 端口、Stream Load 端口、用户名、密码、默认数据库、默认写入数据库、写入批量、写入并发、连接池、SSL 和描述。
- 新增、编辑必须实际写入状态；连接测试必须有测试中、成功、失败和错误反馈。
- “更多”提供真实菜单，例如复制、停用/启用、删除。

### 16.4 机构管理

- 删除工具栏“组织树视图”按钮。
- 新增、编辑、启停、删除都必须真正生效。
- 删除进行引用检查和二次确认。
- 可展示业务系统实例或源数据源关系，但不在机构列表堆叠不必要信息。

### 16.5 数据集详情

所有“查看、查看字段、查看规则、配置”等重复入口统一为“查看详情”，进入同一详情容器的对应 Tab。

必须保留：

- 基础信息；
- 字段结构；
- 同步策略；
- 数据校验；
- 消息通知。

字段表支持分页和横向滚动，列宽稳定；策略保存必须真实更新状态。

### 16.6 数据同步

- 列表支持真实搜索、筛选、分页和每页条数。
- “运行”和“更多”必须有真实行为。
- 详情的运行、暂停/恢复任务、重置水位、删除均有确认、状态反馈和审计。
- 运行批次支持查看配置、查看日志和导出记录。
- 任务详情按基本配置、抽取配置、字段合同、运行批次、校验配置和消息配置组织；字段合同只读展示标准字段、JDBC 真实字段名、Doris 小写字段名和合同版本。

### 16.7 数据预检

- 列表形态参照数据同步：每条采集链路有“详情”和“运行”。每次运行固定扫描整条链路覆盖的源视图，不提供仅检查某一家机构的运行模式。
- 详情是独立 URL 页面，不使用重复的旧抽屉。
- 详情 Tab：基本配置、运行记录、问题汇总。
- 不提供数据样例和行级问题明细。
- 运行展示完整状态推进，不固定在 64%。
- 批量预检实际改变选中项状态；同链路并发限制在服务端校验。
- 问题汇总支持查询、重置、分页和按筛选直接导出 XLSX/CSV 汇总表；不导出行级详情或样例，不建立异步导出任务表，不长期保存导出文件。

### 16.8 数据校验

- 校验详情用于查看，运行用于实际发起校验，两者不得同一行为。
- 全量、修改、删除校验具有独立执行语义和历史。
- 历史刷新、与上次对比、重新校验、窗口校验和差异汇总导出必须真实工作；小型差异汇总数组保存在 `validation_run.difference_summary JSONB`，不建立独立差异表，不导出逐行差异或建立异步导出任务表。
- 当前校验上下文必须绑定当前行任务，不能复用上一次选中的任务。

### 16.9 个人中心和退出

- 用户菜单包含个人中心和退出登录。
- 个人中心包含账户信息、修改密码、告警设置。
- 修改密码校验当前密码、新密码至少 8 位、两次一致；成功后退出重新登录。
- 退出登录需确认、清理会话并进入登录页。

## 19. 新旧系统替换与元数据库基线

### 19.1 新旧系统隔离

- 老项目继续连接原 PostgreSQL 数据库并正常运行，直到新项目完整验收并正式替换；本项目不修改老项目代码、数据库结构或 Flyway 状态。
- 新项目从独立、全新的 PostgreSQL 数据库开始，开发、联调和验收均不得与老项目共用元数据库。
- 两套系统的数据库、Quartz 调度器、同步执行、校验、水位和消息发布必须完全隔离，避免重复调度、重复写入或交叉推进状态。
- 老库结构导出只作为识别历史模型、字段、索引和约束的只读证据，不是新系统数据库基线，也不得放入 Flyway 自动扫描目录。
- 最终替换前单独制定切换方案，明确哪些机构、数据源、数据集、链路和任务配置需要迁移；旧执行历史、Quartz 运行状态和已废止模型默认不自动迁移。

### 19.2 新系统 Flyway 基线

- 新系统采用 Flyway 管理 PostgreSQL 元数据库，空数据库从 `V1__baseline.sql` 自动初始化。
- `V1` 必须依据本业务基线、最终实体模型、数据库约束和索引重新生成，不能直接复制老库结构、旧 `init.sql` 或按文件名重放历史 `migration_*.sql`。
- 老项目数据库不执行 `V1`，不写入 `flyway_schema_history`，也不使用 `baseline-on-migrate` 自动认领。
- 新系统发布后的每次结构或基础数据变化都必须新增不可变的版本化迁移；已经在任何环境执行的版本文件禁止修改、重命名或删除。
- 正向迁移 SQL、迁移前检查、迁移后验证和回退/前向修复说明必须与代码在同一次变更中提交；不允许只改实体或手工改库而不维护 SQL。
- 破坏性变化采用“扩展—迁移—收缩”方式分版本实施；回滚脚本作为运维说明保留在 Flyway 扫描目录之外，生产失败优先使用新的前向修复版本。
- 新增表、字段、约束和索引必须与实体及查询路径一致；数据库唯一约束是任务唯一性等并发规则的最终保证，不能只依赖应用层查询。
- 每次发布至少验证“空库执行全部迁移”和“上一正式版本升级到当前版本”两条路径，服务启动前必须由 Flyway 明确判断数据库版本。

老库只读结构快照及详细维护规范见 `spec/DATABASE_MIGRATION_BASELINE.md`。

## 21. 覆盖和废止的旧规则

以下旧描述不再作为实现依据：

1. **“强制预检阻断任务创建或运行”**：已废止。预检只展示事实和风险，不是准入门禁。
2. **“独立结构校验决定是否允许建任务”**：已废止。结构检查并入预检第一阶段，也不作硬门禁。
3. **“预检保存行级问题明细和业务主键”**：已废止。只保留字段级和组合规则级汇总。
4. **“预检提供数据样例”**：已废止。
5. **“预检自动调度”**：已废止。预检仅人工发起。
6. **“任务失败自动重试、独立断点重试或自动暂停任务”**：已废止。失败只终止本次执行并告警，不改变后续自动调度；是否暂停任务或人工重新采集由维护人员决定。
7. **“一个任务覆盖多家机构”**：已废止。链路可覆盖多机构，任务只归属单机构。
8. **“每个机构复制一条共享链路”**：已废止。共享源对象保持一条链路，不同机构建立单机构任务。
9. **“正式同步使用 raw_ 数据”**：已废止。`raw_` 只用于预检，正式同步始终重新读取源视图。
10. **“Doris 正式表可在 STRICT/PERMISSIVE 间配置或切换”**：已废止。`ods_` 固定使用正式医共体合同，`raw_` 固定使用预检字符串合同，两类表不支持相互转换。
11. **“无主键任务清空整张共享 ODS 表”**：已废止。多个机构共用 `ods_`，无主键任务只能清理并重载当前机构范围。
12. **“标准同步任务可以直接配置 CUSTOM_SQL”**：已废止。标准任务只使用表、视图或物化视图；复杂查询由源系统固化为稳定源对象。
13. **“标准链路支持人工源字段重命名映射”**：已废止。源字段与标准字段只允许大小写差异，字段集合必须完全相等；系统仅保存只读解析快照。
