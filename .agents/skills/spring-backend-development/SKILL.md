# Spring 后端开发

## 工作目标

按照当前项目的架构和工程约定完成后端变更，保持业务语义、模块边界和运行兼容性。不要用通用最佳实践覆盖项目中已经确认的设计。

## 开始前

1. 读取适用范围内的 `AGENTS.md`、项目规范、需求结论和迁移基线。
2. 检查 `pom.xml`、Gradle 文件及源码，确认 JDK、Spring、构建工具、ORM/SQL 框架、测试框架和模块依赖。
3. 查找同类功能，优先沿用现有包结构、命名、分层、异常、响应、日志和配置方式。
4. 确认用户要求是分析、评审还是实施；未授权修改时只给出证据和结论。

不要假设项目使用 JPA、MyBatis、Lombok、MapStruct、Flyway、Nacos、Seata、RabbitMQ 或 Redis。只有仓库已经使用或需求明确要求时才沿用。

## 实施流程

### 1. 确定变更边界

- 从入口追踪到 Service、领域逻辑、持久层、配置、消息和外部依赖。
- 区分现有行为、目标行为和历史兼容要求。
- 只修改实现目标所需的文件，不进行无关重命名、格式化或全局重构。
- 若需求选择仍会改变核心能力，先使用 `$pragmatic-requirements-design` 处理阻塞问题。
- 用户指定某种状态、锁、消息或中间件，只代表采用该约束，不代表可以继续扩展新的状态、字段、配置、恢复流程或统计模型。

### 2. 遵循现有架构

- Controller 负责项目既有的协议适配和校验，不把新业务规则随意堆入入口层。
- Service、领域对象和持久层按当前项目模式分工；项目没有某一层时不要强行补层。
- 区分持久化对象、请求对象和响应对象；是否复用以项目现状和兼容性为准。
- 复用统一异常、错误码、响应结构、审计和日志规范。
- 不吞异常，不把失败记录成成功，也不要只记录日志后继续返回正常结果。

### 3. 处理关键技术边界

- 把事务放在能够保证已确认原子性的最小边界；注意异常传播、批处理和远程调用影响。
- 使用项目现有的幂等、锁、重试、补偿和分布式事务机制；没有明确需求时不要新增复杂机制。
- 设计重试、补传或失败恢复前，先区分任务定义、执行实例和执行记录，并复用现有调度、状态、日志和结果模型。
- 自动重试只实现已确认的触发、次数、间隔和终止语义。不要自行增加指数退避配置、锁续期、宕机回收、专属恢复状态或额外生命周期。
- 理论上可能发生的进程崩溃、网络抖动和锁过期，不足以单独证明需要复杂恢复模型；只有现有执行模型无法客观记录或会造成实质数据风险时才增加必要处理。
- 修改消息生产或消费时，保持路由、载荷、顺序、确认、重试和空值语义兼容。
- 修改缓存时，明确键、过期、更新和失效时机，避免缓存与数据库语义分叉。
- 修改配置时沿用现有配置来源和命名，不硬编码环境地址、密码或令牌。
- 修改调度任务时复用现有任务、执行记录和日志模型，不另建重复生命周期。

### 4. 协同接口与数据库

- 影响 Vue 调用的接口时，同时使用 `$java-vue-api-contract` 核对契约和所有调用方。
- 涉及数据库结构时，同步维护项目规定的迁移脚本、基线或结构文档。
- 评估非空、默认值、历史数据、索引、锁表和回滚影响；不要只修改实体类。
- 复杂 SQL 或性能敏感路径以实际数据库方言、执行计划和数据量为依据，不凭印象改写。

## 验证

1. 先运行受影响模块的编译、单元测试和静态检查。
2. 对数据库、消息、缓存或外部服务边界，使用项目已有的集成测试或可安全执行的替代验证。
3. 检查失败路径、事务回滚、空值、重复请求、权限和兼容场景中与本次变更相关的部分。
4. 再运行仓库要求的更广泛验证；不要因为全量测试耗时就省略最直接的目标测试。
5. 审查最终差异，确认没有无关修改、调试代码、临时配置或敏感信息。

不要为了让测试通过而降低断言、删除测试或隐藏异常。无法运行验证时，明确说明原因和剩余风险。

## 完成输出

简要说明：

- 实现或修复了什么；
- 关键设计和兼容性处理；
- 数据库、配置、消息或接口是否受影响；
- 执行的验证及结果；
- 未验证内容和后续注意事项。
