# Java/Vue 前后端契约

## 工作目标

让后端接口、前端调用和实际业务语义保持一致。先核实项目真实约定，再做最小范围修改；不要凭通用习惯重写已有契约。

## 开始前

1. 读取适用范围内的 `AGENTS.md`、项目规范和已确认需求。
2. 检查构建文件和源码，确认 Java、Spring、Vue、TypeScript、HTTP 客户端及接口文档方案，不要猜测版本或框架。
3. 找到后端入口、请求/响应模型、前端 API 封装、类型定义和所有调用方。
4. 区分审查与实施：用户只要求分析或评审时，不修改文件；用户要求实现时，完成必要修改和验证。

若接口行为尚未确认，且不同选择会改变用户能力、数据模型、安全或兼容性，先使用 `$pragmatic-requirements-design` 处理该阻塞问题。非阻塞细节沿用现有项目约定。

## 契约核对流程

### 1. 建立影响范围

逐项核对：

- HTTP 方法、路径、认证和权限；
- Path、Query、Header、Body、文件参数；
- 请求与响应外层结构；
- 字段名称、类型、必填、可空、默认值和只读规则；
- 校验规则及错误码、错误信息；
- 枚举值及未知值处理；
- 日期、时间、时区和格式；
- 金额、精度、小数、长整型 ID 和 JSON 序列化；
- 分页参数、排序、总数和列表字段；
- 上传、下载、文件名和内容类型；
- 旧调用方、第三方调用方及兼容要求。

把当前实现、目标契约和受影响调用方区分清楚。不要因为现有前端可以容错，就忽略后端契约问题。

### 2. 确定最小兼容改法

- 优先保持已有接口结构和项目统一响应模型。
- 新增字段通常采用兼容性扩展；删除、重命名、改类型或改语义前，查找全部调用方。
- 不为单个接口创建新的响应外壳、分页模型、错误体系或日期格式。
- 服务端校验作为最终依据；前端校验用于交互反馈，两端规则不得相互矛盾。
- 不擅自把空值改成空字符串、零、空数组或默认枚举；沿用已确认业务语义。
- 不擅自改变枚举编码、金额精度、时间含义和 ID 类型。

### 3. 同步实施

实施时按实际影响更新：

- 后端 Controller、请求 DTO、响应 DTO/VO、映射、校验和接口文档；
- 前端 API 方法、参数组装、类型定义、表单、表格、详情和状态展示；
- Mock、测试、示例数据及必要文档；
- 所有直接和间接调用方。

不要为了契约变更顺带重构无关模块。发现后端和前端约定冲突时，以已确认需求和项目权威文档为准，不静默选择一方。

## 验证

根据项目现有能力执行最小充分验证：

1. 搜索旧字段、旧路径和旧枚举的剩余引用。
2. 运行受影响的 Java 编译和测试。
3. 运行前端类型检查、测试、lint 和构建中适用的命令。
4. 对关键接口验证成功、校验失败、空数据、权限失败和兼容调用。
5. 检查生成的接口文档或类型是否与实现一致。

无法执行某项验证时，明确说明未验证内容和原因，不把“代码已修改”表述为“功能已验证”。

## 完成输出

简要说明：

- 变更了哪些接口和字段；
- 后端、前端及调用方分别受到什么影响；
- 是否存在兼容性变化；
- 执行了哪些验证及结果；
- 仍有哪些未验证风险。
